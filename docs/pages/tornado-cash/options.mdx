# Deposits and withdrawals

`prepareShield` chooses pools. `prepareUnshield` chooses how the notes get spent. The amount on both calls is in the asset's base units and has to match live denominations. See [shield and unshield](/tornado-cash) for the short path.

## Deposit strategy

The second argument of `prepareShield` is a strategy, or omitted.

```ts
import { DepositStrategy } from '@kohaku-eth/tornado-cash'

await tornado.prepareShield(asset, { strategy: DepositStrategy.MinFee })
await tornado.prepareShield(asset, { strategy: DepositStrategy.MaxAnonimitySet })
```

| Strategy | How the amount is split |
| --- | --- |
| `MinFee` | Largest denominations first. 1.3 ETH on mainnet is one 1 ETH note and three 0.1 ETH notes. This is the default. |
| `MaxAnonimitySet` | The whole amount goes into the smallest pool for that asset. 1.3 ETH is thirteen 0.1 ETH notes. |

The enum name is `MaxAnonimitySet`. More notes means more deposit transactions, more proofs on the way out, and a larger set of people who used that denomination.

A remainder that does not fill a pool is not deposited. 0.15 ETH with a 0.1 ETH minimum becomes a single 0.1 ETH note under `MaxAnonimitySet`, and the same under `MinFee` when 0.1 is the only pool that fits. Sum the transaction values and show that sum in the confirmation.

ERC-20 shields emit an approval and a deposit for each note. The user's public account needs the token and enough ETH for gas.

The CLI always passes `MinFee`, in `prepareProtocolShield` in [`src/utils/plugins.ts`](https://github.com/kassandraoftroy/kohaku-cli/blob/main/src/utils/plugins.ts).

## ERC-4337 paymaster withdrawal

Use the paymaster relay/broadcast path by passing `mode: 'paymaster'` explicitly; omitting it selects the SDK's regular relayer mode.

```ts
import { createTCBroadcaster, TornadoPaymasterConfigs } from '@kohaku-eth/tornado-cash'

const operation = await tornado.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  delegation: { mode: 'deterministic' },
  tailCalls: async (sender) => [
    {
      to: token,
      data: encodeTransfer(sender, recipient, dust),
      value: 0n,
    },
  ],
  tailCallsGasEstimate: 80_000n,
})

const receipts = await createTCBroadcaster(host, {
  paymasterConfig: TornadoPaymasterConfigs,
}).broadcast(operation)
```

The paymaster sponsors gas. The user's public account does not pay the withdrawal. The broadcaster submits the prepared ERC-4337 user operation to the bundler and waits for its receipt. `receipts[n].id` is a user operation hash, not a separate receipt for each note.

Every paymaster unshield pays the EIP-7702 sender first, including a single note; without user tail calls, the execution phase forwards the amount minus the fee to the requested recipient. This avoids the paymaster rejecting the nonzero execution gas limit that bundlers inject during estimation. When an unshield spends multiple notes, the SDK consolidates them into this same user operation automatically. The first note covers paymaster sponsorship for the whole operation. Subsequent notes run as direct pool withdrawals in the execution phase (tail calls) of that same user operation. You do not need to supply `tailCalls` to enable this consolidation.

User-supplied `tailCalls` run after those withdrawals in the same user operation. The callback receives the sender that will execute them. `tailCallsGasEstimate` is a fallback gas budget for that phase. Bundler estimation is required; estimates can increase the conservative gas floors, and the final signed operation is estimated again after fee/proof changes.

### Delegation

`delegation` picks the account that signs the EIP-7702 authorization and the user operation. It is honored for all paymaster unshields, including a single note. The delegator holds the withdrawn funds along the way and may receive unused-gas refunds after forwarding, so use a key the wallet can recover. The default is derived from the first note; `random` explicitly opts out of recovery.

| Value | Delegator |
| --- | --- |
| omitted, or `{ mode: 'deterministic' }` | An ephemeral address derived from the batch's first deposit. Recoverable from the seed. |
| `{ mode: 'deterministic', path }` | The key at `path`, via `keystore.deriveAt`. Use a normal wallet path when you want a stable address. The host must allow that path. The plugin lets the worker derive exactly this path, nothing else outside `m/29795'/1'`. |
| `{ mode: 'random' }` | A throwaway key. The funds sitting on it during the call are unrecoverable if the user operation stalls. |

```ts
await tornado.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  delegation: { mode: 'deterministic', path: "m/44'/60'/0'/0/3" },
  tailCalls: async () => extraCalls,
})
```

The CLI builds this delegation in [`src/utils/tornado-unshield-delegation.ts`](https://github.com/kassandraoftroy/kohaku-cli/blob/main/src/utils/tornado-unshield-delegation.ts) and submits through a Tor-aware paymaster client from `broadcastTornadoPrivateOp`.

## Picking a path

Use `MinFee` when you want the fewest deposit notes. Use `MaxAnonimitySet` when the product wants every note in the smallest denomination. For withdrawals, use `mode: 'paymaster'` and broadcast through `createTCBroadcaster`. Add `tailCalls` when the withdrawal should continue into further calls.
