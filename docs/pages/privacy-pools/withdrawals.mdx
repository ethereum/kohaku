# Withdrawals

`prepareUnshield(asset, recipient, options)` builds a private operation. `createPPv1Broadcaster` submits it. Use the ERC-4337 paymaster relay/broadcast path as the default integration path. Pass `mode: 'paymaster'` explicitly on both preparation and fee previews; omitting it selects the SDK's regular relayer mode.

Call `estimateUnshield` for the fee preview. It uses the same `mode`, `tailCalls`, and `tailCallsGasEstimate` fields, and it does not generate a proof or validate amount obfuscation. `prepareUnshield` estimates again when you are ready to submit, so a preview can go slightly stale.

```ts
const preview = await pools.estimateUnshield(asset, recipient, {
  mode: 'paymaster',
})
```

`asset.amount` is the gross withdrawn from the pool, unless you set `exact`. The recipient receives `preview.netAmount`.

## Paymaster

The paymaster sponsors an ERC-4337 user operation. The plugin needs a `paymasterConfig` for the chain. The bundled map is the default. See [configuration](/privacy-pools/configuration).

```ts
const operation = await pools.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
})

const broadcast = await createPPv1Broadcaster(host, { broadcasterUrl }).broadcast(operation)
const { txHash } = await broadcast.wait()
```

`broadcasterUrl` is a required constructor field, but paymaster broadcasting uses the bundler URL carried by the prepared operation.

`broadcast()` resolves as soon as the bundler accepts the user operation, and `broadcast.requestId` is its hash. `wait()` polls for the receipt and returns the `txHash` of the transaction that included it. Wallets that track the hash themselves can skip `wait()`, but must check the receipt's `success` field.

If the send request fails, for example on a timeout, `broadcast()` asks the bundler whether it got the user operation anyway, using the hash computed when it was signed (`operation.withdrawal.userOpHash`). If it did, or if the bundler answers that it already has it (`Already known`, e.g. when the same operation is broadcast again), `broadcast()` resolves as usual. Some bundlers only know user operations once they are mined, so if the bundler does not know it and never answered the send, `broadcast()` throws `unconfirmed` with the hash instead of reporting a failure.

Both calls throw a `PaymasterBroadcastError`, whose message is safe to report because it never includes the signed user operation. Its `failure` field says what happened:

| `failure` | Thrown by | Meaning |
| --- | --- | --- |
| `not-accepted` | `broadcast()` | The bundler answered the send request with an error and does not have the user operation, so it will not land. `userOpHash` is set. A different operation from the same sender, for example an earlier attempt at this withdrawal, may still be pending. |
| `reverted` | `wait()` | Mined with `success: false`. Notes spent before the revert stay spent, and their funds may be held by the sender. `txHash` is set. |
| `unconfirmed` | `broadcast()`, `wait()` | The outcome is unknown and the user operation may still land. Do not report it as failed. `userOpHash` is set. After `wait()`, call it again to keep checking. |

The fee is the sponsored gas, priced into the pool asset (`fee` and `gasFeeWei` on the estimate). The broadcaster posts the user operation to the bundler. The user's public account does not need ETH for gas.

### Where the refund goes

The paymaster pre-charges a gas budget and refunds `fee - actualGasCost` in `postOp`. `refundRecipient` is that address. It defaults to the withdrawal recipient, so the recipient can receive a little more than `netAmount` once the refund lands.

```ts
await pools.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  refundRecipient: payer, // a change address you control
})
```

Point `refundRecipient` at a payer or change address when the recipient should see a clean amount.

### Several notes, one user operation

`batch: true` spends enough approved notes to reach `amount` inside one sponsored ERC-4337 user operation. The first selected note (the largest) covers paymaster sponsorship for the whole operation. Subsequent notes run as direct pool withdrawals in its execution phase (tail calls). Any user-supplied `tailCalls` run after those withdrawals in the same user operation; each note does not require its own user operation.

```ts
await pools.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  batch: true,
})
```

Leave it off to spend a single note. If one note cannot cover `amount` while retaining the required change, the call throws.

### Amount obfuscation

Fully spending several notes exposes their exact balances together, making
amount-based correlation with deposits easier. `prepareUnshield` defaults to
`obfuscateAmounts: true` for both paymaster and regular relayer withdrawals.

The requested total is preserved. Only approved notes of the requested asset
are used, largest first, and every selected note retains at least 1%. If one
note can supply the amount while retaining 1%, it is used alone. That amount is
fixed by the request, so no random split is needed. Otherwise, each non-final
note retains a cryptographically random 1–25% where feasible. The final note
supplies the remainder and can retain more than 25%, but never less than 1%.
If the request equals the largest note's balance, at least two notes are needed;
without another eligible note, preparation fails.

The inclusive gross ceiling is the smaller of `floor(approvedBalance * 97 / 100)`
and the total available after reserving 1% of each note, rounded up to base units.
This applies even to single-note withdrawals. Above it, preparation throws
`PPv1AmountObfuscationError` before proofs or signatures, with `requestedAmount`
and `maxObfuscatedAmount` (both gross). With `exact`, fees count toward the ceiling.

The SDK never adjusts the requested total. Explicitly set `obfuscateAmounts: false`
to bypass the ceiling and permit full-note spends. If protection requires multiple
notes, preparation requires paymaster mode with `batch: true`; it otherwise throws.

Near the ceiling, random ranges narrow to leave enough funds for subsequent notes.
Integer rounding can make tiny allocations deterministic.

The allocation is sampled once and retained through fee refinement. Change
follows the existing note lineage and is recovered by normal sync. This removes
exact full-balance matches, but the batch still links withdrawals. Nearby deposit
amounts, timing, later change withdrawals and the aggregate total can still
identify a sender. No anonymity-set improvement has been measured or guaranteed.

### Calls after the withdrawal

`tailCalls` receives the sender address and returns extra transactions that run in the same user operation. `tailCallsGasEstimate` is the gas budget for that execution phase.

```ts
await pools.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  tailCalls: async (sender) => [
    {
      to: token,
      data: encodeTransfer(sender, somewhere, extra),
      value: 0n,
    },
  ],
  tailCallsGasEstimate: 80_000n,
})
```

`estimateUnshield` needs the same `tailCalls` (or at least their presence) and the same gas estimate, or the preview will miss the execution phase.

### Bundler gas bounds

The bundler's gas price is checked independently against the host provider. The SDK requests `eth_feeHistory` for the latest ten blocks at the gas-weighted 90th percentile, then takes the highest per-block tip sample so short spikes are not averaged away. The tip ceiling is `min(20 gwei, max(2 gwei, 3 × sampled tip))`; the total-price ceiling remains three times the latest mined block's base fee plus that tip allowance. The 20 gwei ceiling applies to the tip, not the base fee or total price. Errors include both requested prices and ceilings in wei.

If fee history is unavailable or malformed, the SDK uses the latest block's base fee and `eth_maxPriorityFeePerGas`, with the same formula and hard cap. An unavailable or malformed tip suggestion leaves only the 2 gwei allowance; missing history never automatically grants the full 20 gwei. Without a valid base fee, preparation stops. These bounds can still reject a quote during an unobserved spike or above the hard cap. Validation limits remain bounded at twice the local baseline. Pre-verification gas has a payload-sized ceiling of twice `(350,000 + 40 × calldata/paymaster-data bytes)` rather than a fixed limit.

Tail-call execution gas uses the buffered bundler estimate instead of being held at the old 300,000-gas default. `tailCallsGasEstimate` is an initial estimate. Optional `maxGasLimits` provides absolute ceilings after buffering, for example `{ callGasLimit: 5_000_000n }`. You can replace individual validation or pre-verification ceilings with the same option. A violation throws instead of silently reverting to baseline gas. Pass the same limits to `estimateUnshield` when setting them for preparation; its preview still uses baseline gas and is not a simulation of the tail calls.

There is no default execution-gas ceiling: without an explicit `callGasLimit` ceiling, the bundler can increase the proof-bound fee through its execution estimate, up to the sponsoring withdrawal's affordability limit. Review that fee or set an absolute ceiling when using an untrusted bundler.

There is no percentage-of-withdrawal fee cap. Spending most of a small sponsoring withdrawal on gas is permitted, provided it covers the fee. Bundler estimation and broadcasting use `host.network.fetch`, including receipt polling, so hosts with URL allowlists must permit their configured bundler. The host provider supplies the fee-market reference independently of any custom data service; custom `IDataService` implementations need no new methods. Custom low-level state managers must forward the provider/network supplied by the plugin when using the built-in paymaster helpers.

Preparation sends a signed operation with a valid proof to the bundler for estimation before broadcasting, so the bundler could submit that provisional operation. Show the proof-bound fee and do not treat preparation as a dry run.

### Who signs the user operation

`delegation` chooses the ephemeral sender.

| `delegation` | Sender |
| --- | --- |
| omitted, or `{ mode: 'deterministic' }` | Derived from the note index. A stuck sender can be recovered from the seed. |
| `{ mode: 'random' }` | A one-off key that is discarded. A single-note withdrawal without `tailCalls` pays the recipient during validation. With `batch` or `tailCalls`, funds pass through the sender and any amount left there is permanently inaccessible. |

Do not use `random` in production unless you knowingly accept irreversible loss of any sender balance. A failed execution, an empty `tailCalls` result, or calls that forward less than the payout can leave funds there even if the sponsoring note was successfully withdrawn. Prefer `deterministic` unless you have a specific reason to throw the key away.

The CLI's paymaster wiring is [`src/utils/privacy-pools-paymaster.ts`](https://github.com/kassandraoftroy/kohaku-cli/blob/main/src/utils/privacy-pools-paymaster.ts) and the unshield flow in [`src/lib/unshield-flow.ts`](https://github.com/kassandraoftroy/kohaku-cli/blob/main/src/lib/unshield-flow.ts).

## Exact output

Set `options.exact` when `asset.amount` is the amount the recipient must receive, and the gross should grow to cover the fee.

```ts
const operation = await pools.prepareUnshield(
  { asset, amount: 1_000_000n }, // recipient gets 1 USDC (6 decimals)
  recipient,
  {
    mode: 'paymaster',
    refundRecipient: payer,
    exact: { gasBumpBPS: 1_500n },
  },
)

operation.exact
// { grossAmount, requestedNet, expectedNet, fee }
```

`gasBumpBPS` adds headroom to the quote's gas component. `10000` is 100%, so `1500` is 15%. That is the default, exported as `DEFAULT_EXACT_GAS_BUMP_BPS`. The bump applies to the gas term, and the fee still has to fit the asset's on-chain max relay fee. If it does not, the call throws.

`refundRecipient` is required. The gross is sized from the worst-case gas fee, and the overcharge comes back in `postOp`. The call throws if you omit the refund address.

```ts
const operation = await pools.prepareUnshield(asset, recipient, {
  mode: 'paymaster',
  refundRecipient: payer,
  exact: {},
})
```

Send the refund to `payer` and the recipient nets `requestedNet`. Send the refund to `recipient` and they receive at least `requestedNet`. In that case `operation.exact.expectedNet` is a lower bound.

If the built operation would deliver less than `requestedNet`, `prepareUnshield` throws `PPv1ExactOutputError`. `requestedNet` and `expectedNet` are on the error. Raise the balance, lower the amount, or widen the fee headroom and try again.

## Integration default

Use `mode: 'paymaster'` for withdrawals, including those without batching or follow-up calls. Show `estimateUnshield` with the same mode before confirmation, then broadcast the prepared operation with `createPPv1Broadcaster`.
