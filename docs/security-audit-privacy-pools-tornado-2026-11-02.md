# Privacy Pools v1 and Tornado Cash security review — 2026-11-02

## Follow-up on `fix/final-audit-fixes`

- **H-01 — documented accepted risk** in `4f961f50`. Both packages now warn in their delegation type comments, READMEs, and user docs that `random` discards the signing key and can irreversibly strand funds. Tornado's warning also covers the post-operation gas refund. This changes no runtime behavior.
- **H-02 — fixed** in `070dc6eb`. Tornado signs the first note envelope twice per manager session and rejects a signer whose canonical `(r,s)` differs. Its configuration guide states that signatures must remain reproducible across sessions. This first-use check cannot prove that a signer will remain deterministic forever.
- **M-02 design note — aligned** in `221eca2a`. Tornado now uses the current EOA transaction count for an explicit `delegation.path` authorization, as Privacy Pools does. Note-derived and random senders continue to authorize at EOA nonce zero, which on-chain authorization validation checks; every sponsored UserOperation still has EntryPoint nonce zero. Tests cover all three cases.

This report retains the original findings below as the audit record. The follow-up commits were intentionally kept separate; this Markdown file is untracked and is not part of any commit.

## Scope and confidence

Reviewed the current `kohaku` checkout (`adfcb4656aa01f8cd5003805945644f52dece5d9`): `packages/privacy-pools` (`0.1.0-alpha.36`) and `packages/tornado-cash` (`0.1.0-alpha.33`), focusing on note derivation, sync/root verification, withdrawal proofs, relayer fees, sponsored withdrawals, gas limits, and EIP-7702 execution. I also reviewed the direct paymaster contracts and vendored EntryPoint/Simple7702Account source at `../kohaku-contracts/privacy-paymaster` (`kohaku-contracts` commit `1b23e91a06fb4af50220507febf38bd05078e6a4`). Both packages select the [Simple7702Account at `0xe6Cae83BdE06E4c305530e199D7217f42808555B`](https://etherscan.io/address/0xe6Cae83BdE06E4c305530e199D7217f42808555B#code). I did not compare deployed bytecode to the vendored source or run a funded mainnet fork.

This is a source review, not a claim that every path is safe. **I found no demonstrated critical bug or permissionless theft of another user's notes.** H-01 is a high-impact recovery risk in an explicitly unrecoverable mode and can be accepted with a precise warning; H-02 is a conditional High bug for custom signers. The availability and migration concerns follow separately. Spending nearly all of a 0.01 ETH Tornado note on sponsorship is an intended feature and is **not** counted as a vulnerability here.

## High-impact findings

### H-01 — Random 7702 delegation can permanently trap funds (candidate accepted risk)

**Affected:** Privacy Pools v1 with `delegation: { mode: 'random' }` plus batch withdrawal or `tailCalls`; Tornado Cash with `delegation: { mode: 'random' }` (including a single note). **Impact:** irreversible loss of the sponsoring note's net payout if execution fails. Tornado can also lose the unused gas-fee refund when execution succeeds.

Both implementations generate a fresh private key in memory and return only a signed UserOperation, with no key export or durable recovery path ([Privacy Pools `resolveSigner`, lines 343–355](../packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L343-L355); [Tornado `resolveBatchDelegator`, lines 174–195](../packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts#L174-L195)). Privacy Pools pays the sender when it needs an execution phase ([lines 124–133, 167–174](../packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L124-L174)). Tornado always pays the sender first, then forwards or runs caller-supplied calls ([lines 190–247](../packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts#L190-L247)).

The paymaster consumes the sponsoring note during ERC-4337 **validation** ([`BasePrivacyPaymaster._validatePaymasterUserOp`, lines 136–164](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/BasePrivacyPaymaster.sol#L136-L164); [direct Tornado withdrawal, lines 63–76](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/tornadocash/TornadoPaymaster.sol#L63-L76)). EntryPoint executes `callData` afterward and records a failed execution without reverting the earlier validation ([`handleOps`, lines 58–74](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/lib/account-abstraction/contracts/core/EntryPoint.sol#L58-L74); [`innerHandleOp`, lines 401–422](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/lib/account-abstraction/contracts/core/EntryPoint.sol#L401-L422)). `execute`/`executeBatch` revert if an inner call fails ([`BaseAccount`, lines 47–76](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/lib/account-abstraction/contracts/core/BaseAccount.sol#L47-L76)). A stale downstream condition, rejecting recipient, or execution out-of-gas can therefore leave the validation payout on an EOA whose key is gone. In a batch, the extra *direct* withdrawals revert with execution and their notes remain; the sponsoring note has already been consumed.

**Concrete failure sequences:** (1) Select random delegation and supply `tailCalls: async () => []`. In a one-note withdrawal, this still selects the sender as the validation payout target, but both builders serialize an empty call list as `callData = 0x` ([Privacy Pools `buildSignedUserOp`, lines 140–157](../packages/privacy-pools/src/paymaster/utils.ts#L140-L157); [Tornado `buildSignedTornadoUserOp`, lines 170–187](../packages/tornado-cash/src/paymaster/utils.ts#L170-L187)). The operation can succeed while the entire net payout remains at the keyless sender. (2) Supply a tail call that reverts after the paymaster withdrawal succeeds. The UserOperation receipt can report unsuccessful execution while the sponsoring nullifier has been spent. Its payout sits at `userOperation.sender`, which the caller cannot sign for after the thunk returns. Gas estimation reduces predictable reverts but cannot guarantee execution against later state. A call list that forwards only part of the payout also strands the remainder with random delegation.

**Additional successful-operation loss in Tornado:** `TornadoPaymaster` sets `refundRecipient = d.recipient`, which is the random sender ([lines 73–76](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/tornadocash/TornadoPaymaster.sol#L73-L76)). The SDK's forward happens before `postOp`, so an overcharge refund sent afterward cannot be forwarded and remains at that unrecoverable sender ([`BasePrivacyPaymaster._postOp`, lines 167–182](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/BasePrivacyPaymaster.sol#L167-L182)). Privacy Pools' *current old adapter* explicitly routes the refund to the designated recipient, so this successful-operation refund case does not apply there ([lines 169–174, 249–259](../packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L169-L259)). It will need attention when migrating to the direct `PrivacyPoolsPaymaster`, which returns `feeData.recipient` as its refund recipient ([lines 89–102](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/privacypools/PrivacyPoolsPaymaster.sol#L89-L102)).

**Triage / suggested fix:** `random` is an explicit expert option, so this can be accepted as a documented recovery trade-off without removing the mode. The public option/type comment should state that the private key is discarded, a failed or incomplete execution (including an empty `tailCalls` result) can permanently lose the net withdrawal, and Tornado's post-operation fee refund is unrecoverable even on success. The current Privacy Pools type comment calls random safe for a single-note withdrawal without qualifying the `tailCalls` case ([lines 14–25](../packages/privacy-pools/src/interfaces/user-ops.interface.ts#L14-L25)); Tornado's comment says random is only honored with tail calls although the implementation honors it for every sponsored withdrawal ([lines 19–32](../packages/tornado-cash/src/account/delegation.interface.ts#L19-L32)). If the successful-operation refund loss is *not* an intended cost of random mode, route it to a separate user-controlled address; that needs a contract/API change because the direct Tornado paymaster currently binds the refund to the withdrawal recipient. Severity here reflects the potential loss, not a claim that an explicit unrecoverable mode must be prohibited.

### H-02 — Tornado signature-derived deposits can become unspendable with a nondeterministic signer

**Affected:** integrations that supply a custom `EnvelopeSigner`/`secretManagerFactory` with nondeterministic ECDSA signatures. **Impact:** a deposited note can be impossible to rediscover or spend after the manager/session is recreated. The default keystore signer appears deterministic, so this is not a demonstrated default-wallet loss.

Tornado derives each note's nullifier and secret from the EIP-712 signature's `(r,s)` and caches **one** signature per `(chainId, nonce)` for the current manager instance ([`signature-keys.ts`, lines 21–32, 115–160](../packages/tornado-cash/src/account/signature-keys.ts#L21-L160)). Deposit construction uses these derived commitments ([`getDepositPayloadThunk`, lines 97–137](../packages/tornado-cash/src/state/thunks/getDepositPayloadThunk.ts#L97-L137)). Private signature secrets are excluded from saved snapshots and re-derived during sync ([`store.ts`, lines 37–39](../packages/tornado-cash/src/state/store.ts#L37-L39); [`discoverUserEventsThunk`, lines 29–52](../packages/tornado-cash/src/state/thunks/discoverUserEventsThunk.ts#L29-L52)). A valid signer that chooses fresh ECDSA entropy can produce a different `(r,s)` for the *same* envelope after restart. The new commitment does not match the deposit, and the original nullifier/secret are absent from the snapshot. The public plugin permits a custom manager ([`plugin/base.ts`, lines 90–95](../packages/tornado-cash/src/plugin/base.ts#L90-L95)); `SignatureSecretManager` itself accepts a custom envelope signer ([lines 75–77, 106–120](../packages/tornado-cash/src/account/signature-keys.ts#L75-L120)).

Privacy Pools already guards this failure class by signing the first envelope twice per manager session and refusing derivation if canonical signatures differ ([`signature-keys.ts`, lines 165–226](../packages/privacy-pools/src/account/signature-keys.ts#L165-L226)); Tornado has no equivalent check. Tornado's signature-cache test explicitly expects one signing call for the first `(chainId, nonce)` ([`signature-keys.test.ts`, lines 118–144](../packages/tornado-cash/tests/unit/signature-keys.test.ts#L118-L144)). Privacy Pools' configuration guide explains the deterministic-signature requirement; Tornado's current secret-manager guide does not ([Privacy Pools guide](../docs/pages/privacy-pools/configuration.mdx#L75-L79); [Tornado guide](../docs/pages/tornado-cash/configuration.mdx#L108-L131)).

**Suggested fix:** add the same determinism check before Tornado can produce a deposit commitment, with an explicit opt-out only for a signer known to be deterministic, and document that the same canonical `(r,s)` must be reproducible for the same envelope across sessions. Documentation alone tells integrators the requirement but does not stop an incompatible signer from silently creating an unrecoverable note. A saved, encrypted note-secret backup could provide another recovery path. A check on one envelope is a useful safeguard but cannot prove a signer will remain deterministic forever.

## Other material observations (below High threshold)

### M-01 — A malicious ASP gateway can cache a root-valid tree that contains no usable labels

The Privacy Pools ASP root does not commit to the number of leaves. A gateway can return a one-leaf tree containing the real root as its “leaf”: the one-leaf LeanIMT root is that same value, so `checkedLeaves` accepts it ([`syncAspThunk.ts`, lines 14–40](../packages/privacy-pools/src/state/thunks/syncAspThunk.ts#L14-L40); [LeanIMT root/insert, lines 52–55, 78–95](../packages/poseidon-lean-imt/src/limt.ts#L52-L95)). The subsequent on-chain root check also passes, yet a user's actual label is absent and proof construction throws ([`proofFromTree`, lines 44–55](../packages/privacy-pools/src/utils/proof.util.ts#L44-L55)). The bad leaves are cached and `syncAspThunk` skips refetch while the root stays unchanged ([lines 52–64](../packages/privacy-pools/src/state/thunks/syncAspThunk.ts#L52-L64)). This is a persistent local withdrawal denial after a compromised gateway has recovered, until a new root or a state/cache reset. It does not spend the note or let the gateway forge a valid proof. The source already acknowledges the leaf-count ambiguity; the existing ASP tests cover added/dropped labels but not this upper-node substitution.

**Suggested fix:** bind leaf count or a canonical tree shape to the on-chain commitment where possible; otherwise allow a forced refetch/reset and treat an absent expected label as an invalid cached tree. Gateway refusal to serve data can already deny service, so I rate this Medium rather than High.

### Design note — UserOperation nonce zero enforces single-use senders

The hard-coded EntryPoint `nonce: 0n` is an intentional one-shot constraint, **not a liveness bug to fix by fetching the next nonce** ([Privacy Pools, lines 263–273](../packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L263-L273); [Tornado, lines 249–260](../packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts#L249-L260)). A sender that has already submitted a UserOperation on nonce key zero fails EntryPoint nonce validation before the paymaster spends a note ([`EntryPoint._validatePrepayment`, lines 778–800](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/lib/account-abstraction/contracts/core/EntryPoint.sol#L778-L800)). Tornado also signs the EIP-7702 authorization with EOA nonce zero, so an address that has already sent a regular EOA transaction cannot use this path ([`paymaster/utils.ts`, lines 189–197](../packages/tornado-cash/src/paymaster/utils.ts#L189-L197)). Privacy Pools makes an explicit wallet-path exception for the **EOA** nonce: it reads the existing transaction count for `delegation.path` and signs an authorization at that nonce while keeping the UserOperation nonce zero ([lines 158–165](../packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L158-L165)). Thus it still prevents repeat UserOperations, but it does not prevent a first sponsored withdrawal from an EOA with prior transaction history. This exception should be retained or removed according to the intended privacy policy for explicit wallet paths. A received transfer alone does not advance the EOA nonce, so nonce checks do not establish that an address has no balance or inbound history.

### Migration gate — Privacy Pools still uses the previous adapter paymaster ABI

The current Privacy Pools mainnet config points to the old paymaster plus pool adapters ([`config.ts`, lines 18–29](../packages/privacy-pools/src/config.ts#L18-L29)), and it encodes `(adapter, adapterData)` plus four-field `FeeData` ([`adapter-data.ts`, lines 8–63](../packages/privacy-pools/src/paymaster/adapter-data.ts#L8-L63)). The local direct `PrivacyPoolsPaymaster` expects `(pool, withdrawal, proof)` and two-field `FeeData` ([`PrivacyPoolsPaymaster.sol`, lines 20–31, 79–90](/Users/x/dev/personal/kohaku-contracts/privacy-paymaster/contracts/privacypools/PrivacyPoolsPaymaster.sol#L20-L90)). This is expected given the planned migration, but simply changing the address will make sponsored withdrawals fail. Update encoding, allowlist checks, refund routing, and tests together. I did not treat the ABI difference as a live vulnerability.

## Validation and limits

- Focused existing unit suites passed: Tornado `signature-keys` and `paymaster-withdraw-estimation` (25 tests); Privacy Pools `asp-root` and `paymaster-gas-bounds` (22 tests). They do **not** exercise the fund-loss failure sequence or a nondeterministic signer after restart.
- No live withdrawal, funded fork, deployed-bytecode comparison, or proof-of-concept transaction was run. The High findings follow directly from the cited source and EntryPoint phase ordering; deployment-specific behavior should be confirmed before remediation is prioritized.
- I did not audit the old Privacy Pools paymaster's deployed source or every dependency/transitive contract. The direct paymaster review used the code in `kohaku-contracts/privacy-paymaster`, per the repository layout, not Robert-MacWha's fork.
