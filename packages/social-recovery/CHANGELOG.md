# @kohaku-eth/social-recovery

## 0.0.1-alpha.1

### Patch Changes

- 1feee1e: `anonAadhaarMethod()` with neither `stack` nor `artifacts` now proves from anon-aadhaar's public bucket instead of answering every proving and verifying call as unavailable: the installed `@anon-aadhaar/core` initialises with `METHOD_AADHAAR_DEFAULT_ARTIFACTS`. The SDK hosts no proving file. New constants, exported from both entries: `METHOD_AADHAAR_BUCKET_URL`, the bucket's v2 base; `METHOD_AADHAAR_BUCKET_CHUNKED`, the peer's browser mode (the 10 MB wasm and the zkey in ten gzip pieces, 296 MB, cached by the peer in the browser's storage under their file names, so two chunked sources share one cache); `METHOD_AADHAAR_BUCKET_SERVER`, the whole 612 MB zkey, which the peer downloads again on every proof; and `METHOD_AADHAAR_DEFAULT_ARTIFACTS`, equal to `METHOD_AADHAAR_BUCKET_CHUNKED`. The bucket answers cross-origin GET only, and an extension page needs it in its host permissions. `chunked` runs in a browser only: a Node caller that leaves the default sees the peer's storage error surface inside the prover, so the proof reads `material-rejected`; a Node caller passes `METHOD_AADHAAR_BUCKET_SERVER` or `local` paths.

  `anonAadhaarMethod({ artifacts })` keeps its one shape, `{ wasmURL, zkeyURL, vkeyURL, artifactsOrigin }`, and its checks (non-empty strings, a known origin); a stack and artifacts together still throw a `TypeError`. A browser caller holding the files passes `URL.createObjectURL(file)` for each under `server`; `local` is Node only. The peer's `init` is page-global: each stack initialises once, and the last `init` on the page sets the files every stack proves with. `METHOD_AADHAAR_NO_ARTIFACTS_MESSAGE` stays exported for compatibility and is no longer raised.

  `validateSetup`, pure and on the setup client, reports a credential whose config its method's codec cannot decode as the error `credential.config-malformed` (subject `credential`, values `place`, `module` and `bytes`, the config's length in bytes), so a config the module would refuse at every proof, a 64-byte Aadhaar config among them, no longer commits silently. Only the layout is judged. New: the optional member `MethodReads.codec`, the serving implementation's `decodeConfig`, which the setup client fills from the registered implementation; a pure caller without it gets no such judgment, and one whose `codec` has no `decodeConfig` function gets a `TypeError`. New: the error code `credential.config-malformed` in `SETUP_ERROR_CODES`, after `credential.duplicate`.

  Compatibility: every existing call site keeps compiling and running, with one exception. The closed set `SETUP_ERROR_CODES`, and with it the `ErrorCode` union, grew by one member, so a consumer that keeps an exhaustive map or switch over every error code (a `Record<ErrorCode, string>`, an `assertNever` default) must add `credential.config-malformed` before it compiles again; a consumer that reads findings as data is unaffected.

- 1feee1e: Take the digest `place` as the full `uint256` the `PolicyManager` hashes, so a place beyond 2^53 has a typed data and a digest.

  Breaking: the `place` of the `ApprovalMessage` and `CancellationMessage` records, and so of `ApprovalTypedData`, `CancellationTypedData` and a `Ctx`'s typed data, is a `bigint`. `approvalTypedData`, `cancellationTypedData`, `approvalDigest` and `cancellationDigest` accept `place: number | bigint`: a number must be a non-negative safe integer, a bigint must fit `uint256`, and anything else throws a `TypeError` or `RangeError` as before.

- 1feee1e: Drop the unused `creation` member from `ClientConfiguration`: the SDK never read it.

  Breaking: the optional `ClientConfiguration.creation` member and the `CreationRecord` type are removed. A TypeScript integrator still writing `creation` in a configuration literal gets an excess-property compile error, and a missing-export error for `CreationRecord`. At run time the configuration check copies only the members it names, so a `creation` key still passed is silently ignored, neither checked nor kept on the client's configuration, where it was refused with a `TypeError` or `RangeError` when malformed before.

- 1feee1e: Both entries of the `exports` map, `.` and `./recovery-methods`, carry a `default` condition after `types` and `import`, naming the same ESM file as `import`, so a resolver that matches neither `import` nor `require` (a Jest module mapper among them) finds the entry. The package stays ESM only.

  `./recovery-methods` now exports every `METHOD_AADHAAR_*` constant beside the methods, as the core entry already does; the `METHOD_ZKPASSPORT_*` constants stay on the core entry alone.

  `validateSetup` and the setup client's `validateSetup` and `describeSetup` read whether the account holds code, with one `eth_getCode` per judgment shared with the candidate keys' reads. A draft over an account with no code gets one error, `account.not-deployed` (subject `account`, values `account`, `servedImplementation` and `accountImplementation` where configured), and no `action.unsupported`, since the action's fit is unjudgeable before deployment; `action.unaudited` is unchanged. Deploy the account first, or in the transaction that carries the commit. New: the error code `account.not-deployed` in `SETUP_ERROR_CODES`, after `action.unsupported`, and the member `ActionReads.accountHoldsCode`.

  The Aadhaar `replyFrom` reads the QR's signing time before proving and refuses as `material-rejected`, without calling `generateArgs` or `prove`, a QR signed before now by more than the config's freshness window plus `METHOD_AADHAAR_SIGNED_AT_SLACK` (0 seconds: the read is the circuit's own hour-truncated `timestamp` input, so the pre-prover check refuses exactly what the post-prover check would); a QR within that bound, signed in the future or whose time cannot be read is proved as before, and the post-prover freshness check is unchanged. New: the optional stack member `AnonAadhaarStack.signedAt(qrData)`, which the default stack provides by importing `@anon-aadhaar/core` without `init` and reading the time with its `timestampToUTCUnix`, `decompressByteArray` and `convertBigIntToByteArray`; those three are new optional members of `AadhaarCoreSurface`, listed in the new constant `METHOD_AADHAAR_STACK_TIME_CALLS`; a peer without them still loads, and its `signedAt` answers undefined.

  New zkPassport version utilities on the core entry: `zkPassportVersionOf(word)` decodes a trusted-key version word (major, minor and patch as three big-endian `uint16` in its first six bytes, zero after) to `major.minor.patch`, and `zkPassportVersionWord(version)` encodes one, lower-case; both throw a `TypeError` on a malformed word or version. The peer's `getSolidityVerifierParameters(...).version` is that word: compare it by value with `trustedKeys[METHOD_ZKPASSPORT_VERSION_KEY]`. New constants: `METHOD_ZKPASSPORT_VERSION_KEY`, `METHOD_ZKPASSPORT_VERSION_PARTS`, `METHOD_ZKPASSPORT_VERSION_PART_BYTES`.

  The zkPassport `openRequest` on the ceremony and the signing input is documented: scanning one request's code twice makes `@obsidion/bridge` refuse the second handshake with no event on the record, and a page ends such a wait with `cancel()`. No code change.

  The default Aadhaar stack outside test mode now refuses locally only a proof signed by the peer's test key; every other key reaches the peer's `verify`. A key the peer does not know, which it refuses by throwing, therefore answers `not-judged` instead of `rejected`, and `replyFrom` hands such a proof on instead of returning `material-rejected`, leaving the chain to judge it: `@anon-aadhaar/core` 2.4.3 carries UIDAI's 2021 key, while current QRs carry UIDAI's 2026 key, which the module trusts. Test mode is unchanged: only the test key reaches the peer.

  Breaking: `ActionReads` gains the required member `accountHoldsCode`, so a caller of the pure `validateSetup` or `describeSetup` with its own reads must supply it; `describeSetup` does not read it.

- 1feee1e: New on the core entry: `orderVerdict(record, selection, now)`, the gathering's ordering verdict, which `order` and `RecoveryClient.complete` both read, so a completion judges the record once. It returns `{ outcome: 'ordered', proofs }`, the proofs strictly increasing by place (the selection where one is given, otherwise the preferred satisfying set), or `{ outcome: 'refused', reason, findings }`: `window-passed` with the whole window result (errors and warnings, such as `request.moment-skew`), `place-out-of-range` with the rule's findings where any of them is a `proof.place-out-of-range`, or `rule-unsatisfied` with the rule's findings (`request.rule-unsatisfied`). The rule is judged over the chosen places alone and the proofs are built once from the final set, so `order` still reads only the chosen replies' members: an unchosen reply's malformed `method` is not read. It throws a `TypeError` on an unread record and a `RangeError` where the selection names a place no reply fills, as `order` does. New records `OrderVerdict` and `OrderRefusal`; new constants `GATHERING_ORDER_REFUSALS` (frozen: `window-passed`, `rule-unsatisfied`, `place-out-of-range`), `GATHERING_PLACE_OUT_OF_RANGE_MESSAGE` and `GATHERING_ORDER_REFUSAL_MESSAGES`, the frozen map from each reason to the message `order` throws as a `RangeError` and `complete` as a `KitRefusalError` (`GATHERING_WINDOW_PASSED_MESSAGE`, `GATHERING_RULE_UNSATISFIED_MESSAGE`, `GATHERING_PLACE_OUT_OF_RANGE_MESSAGE`). `ruleCountFindings` now takes any `{ body, proofs }` whose proofs carry at least their `place`; its findings are unchanged.

  `complete` no longer runs the request shape guard over its candidate submission, so a hand-edited record with a malformed `account`, `action`, `payload`, `order` or reply proof member is no longer refused with a `TypeError` at `complete`; `prepareStartAttempt` and `prepareCancelByProofs` refuse it before any read, and `addApproverReply` guards replies at filing.

  New: `SetupDescription.action`, of the new type `DescribedAction`, names the action a setup commits as the party that holds the account's authority once armed: its `address`, its own `actionInfo()` answer as `info` (name, version, the ERC-165 probe; self-attested, unanswered where that read failed), whether it is the descriptor's own action (`shipped`), whether the descriptor's audited list names it (`audited`), and its `supportsAccount` answer, absent where the account holds no code yet. `describeSetup` makes no new read for it, and refuses with a `TypeError` a context whose `action.actionInfo` is not an object or whose `action.supportsAccount` or `action.accountHoldsCode` is not a boolean.

  `order` and `complete` keep their signatures and thrown types; these are additions only. One more case changes under `order`: a hand-built record whose chosen places (every filled place with no selection, the selected places otherwise) include one at or past the body's credential count, which `fileReply` never produces, now throws `GATHERING_PLACE_OUT_OF_RANGE_MESSAGE`, as a `RangeError` from `order` (which used to return its proofs) and as a `KitRefusalError` from `complete` (which already refused it). A `SetupDescription` built by hand (an integrator's double) gains the required member `action`.
