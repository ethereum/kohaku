### Changes included from the prerelease series

#### Patch Changes

- 589ee85: An Aadhaar proving call now forwards no progress after its signal aborts or the call settles, and the method documents what an abort stops. The Aadhaar method hands the proving stack the page's `onProgress` gated on the material's `signal` and on the call, so a state reaches the page only until the signal aborts or the call settles with a proof or a failure, and never while the signal throws; an injected stack receives that gated callback as the second argument of `AnonAadhaarStack.prove`, beside the signal as before, and a state it reports through the callback after the call settled reaches nothing. The JSDoc of `AadhaarMaterial.signal`, `AnonAadhaarStack.prove`, `configFrom`, `replyFrom` and `anonAadhaarMethod` states the contract: an abort before or during any step settles that call `device-refused` at once, that call returns no proof or config, and no progress is forwarded after the signal aborts or the call settles. The SDK starts no worker, so the installed `@anon-aadhaar/core` stack's download and proving are not stopped and hold their memory and CPU until they end. A call started meanwhile over the same files proves alongside them; one over other files waits for them to end. An injected stack receives the signal and may stop its own work. `anonAadhaarMethod` moved unchanged into its own source file and stays exported from the `./recovery-methods` entry as before. No record, closed set, constant, device fact or signature changes.

  Compatibility: a page's `onProgress` is no longer called after its signal aborts or the call settles, so a later step's status is no longer overwritten by an aborted proof or by an injected stack that keeps the callback. An injected stack whose `prove` compared the callback it receives with the page's own by identity now receives a wrapper. A page with no `onProgress` sees no change.

- 589ee85: The default Aadhaar stack checks the bucket's code files and reports a failed download as `device-unavailable`. Where the artifacts' `wasmURL` and `vkeyURL` are the SDK's own bucket files, as in `METHOD_AADHAAR_BUCKET_CHUNKED` (the default) and `METHOD_AADHAAR_BUCKET_SERVER`, the installed stack fetches both once per page, before the peer's `init`, compares their sha256 with the new `METHOD_AADHAAR_BUCKET_SHA256` (`wasm`, `zkey` and `vkey` as `0x` lower hex) and hands them to the peer as object URLs. The page keeps one checked pair for each bucket wasm and vkey URL and pinned hashes: concurrent first loads share one fetch, and every later stack over the same files reuses the pair without fetching. That pair is never revoked, since the peer's page-global `init` may still read it, so the retention is bounded at one pair per files and hashes per page; a fetch, check or object URL that fails keeps nothing and revokes any object URL that load made. The zkey URL is unchanged and the zkey is not checked; its hash is for a caller holding a whole copy of its own. A failed fetch or a mismatch rejects the load with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_ARTIFACT_HASH_MESSAGE`. That reads `device-unavailable`, and the load is retried on the next call. Integrator URLs are neither fetched nor changed. The peer's `init` is page-global, so two stacks with different files on one page now take turns on the peer: before each `generateArgs`, `prove` or `verify`, a stack whose files the peer does not hold waits until every peer call in flight under the files it holds has settled, an aborted proof's included, then calls `init` again with its own files, already checked or as given, with no new fetch or check. Calls over the files the peer holds run at once and side by side, as before, while no stack with other files waits its turn; once one waits, every later call queues behind it in arrival order, so a stack with other files is not held off by a steady stream of proofs. Default stacks, which share one pair, never re-initialise each other. A proof whose signal aborts while it waits never reaches the peer, and a failed `init` reads `device-unavailable` and is tried again on the next call. That includes the `init` that `replyFrom` needs before its local verdict when a stack with other files took its turn during the proof, which now answers `device-unavailable` instead of returning the proof unverified, while any other throw from the peer's `verify` still reads `not-judged`, as an unavailable stack still does under the method's `verify`. The JSDoc of `coreStack`, `AnonAadhaarArtifacts` and `AnonAadhaarMethodOptions.artifacts` says so. The stack also records each progress state the peer reports before passing it to the page unchanged. A proof that rejects while the last state is a download state (the new `METHOD_AADHAAR_DOWNLOAD_STATES`, `fetching-wasm` and `fetching-zkey`) rejects with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_STACK_DOWNLOAD_MESSAGE`, which reads `device-unavailable`. A rejection with no state, or at or after `proving`, reads `material-rejected` as before. Under `chunked` the peer drops a zkey piece's download error, so a failed or corrupt piece still reads `material-rejected` and stays in the browser's storage under its file name until the site's data is cleared. The chunked source that last wrote a name is the one every chunked proof on the page reads. The JSDoc of `METHOD_AADHAAR_BUCKET_CHUNKED` and `AnonAadhaarMethodOptions.artifacts` says so. No closed set or record changes.

  Compatibility: a download that fails under the installed stack's `server` mode, or the wasm download under `chunked`, now reads `device-unavailable` instead of `material-rejected`. Over the bucket files, the default stack now fetches the 10 MB wasm and the vkey itself, once per page, and the peer reads them from memory instead of from the bucket on every proof; that pair stays in memory for the life of the page. That uses `fetch`, `Blob` and `URL.createObjectURL`, present in browsers and in Node 22 and later. A bucket file that changes or fails to download stops proving with `device-unavailable` until it matches again. A call through a stack whose files the peer does not hold now waits for the peer's calls in flight to end instead of running at once over another stack's files. What a consumer installs, the bucket records' values and the lazy import of `@anon-aadhaar/core` are unchanged.

- 589ee85: The holder chooses the Aadhaar freshness window, 75 minutes by default, and the setup description shows it. The Aadhaar `enrollInput` takes an optional `freshnessWindow` parameter, named by the new constant `METHOD_AADHAAR_WINDOW_PARAM`. It is a bigint or a safe integer of seconds, at least `METHOD_AADHAAR_MIN_FRESHNESS_WINDOW` (3600) and below 2^256, with no other ceiling. Another type throws a `TypeError` with the new `METHOD_AADHAAR_WINDOW_TYPE_MESSAGE`, and a value out of range a `RangeError` with the new `METHOD_AADHAAR_WINDOW_RANGE_MESSAGE`; both name `freshnessWindow`. The ceremony input now carries `freshnessWindow` as a bigint, `METHOD_AADHAAR_FRESHNESS_WINDOW` where the parameters name none. `configFrom` writes that window as the config's third word. An input without one, such as one made before this change, gets the default. An input whose window is not a bigint of at least 3600 that fits a `uint256` is `material-rejected` before proving. `signingInput` ignores the parameter, since the config holds the window. `describeSetup` returns the new required member `SetupDescription.aadhaarWindows`: for each credential of the deployment's Aadhaar method, in place order, its `place` and the `freshnessWindow` its config holds, in seconds. A window under the minimum is shown as held, and validation still reports it. A config that is not the 96-byte layout of nullifier, seed and window throws a `TypeError` naming `draft.clauses[c].credentials[i].config`. Changed: `METHOD_AADHAAR_FRESHNESS_WINDOW` is now `4500n` (75 minutes) instead of `86400n`. New: `METHOD_AADHAAR_WINDOW_PARAM`, `METHOD_AADHAAR_WINDOW_TYPE_MESSAGE` and `METHOD_AADHAAR_WINDOW_RANGE_MESSAGE`, exported from both entries. The config layout, the codec, the bounds, `replyFrom`, `verify` and the proving arguments are unchanged.

  Compatibility: new Aadhaar enrollments write a 75-minute window instead of 24 hours unless the holder passes `freshnessWindow`. An approval must then reach the chain within 75 minutes of the QR's signing time, which the QR records to the hour, so a freshly downloaded QR stays usable for at least 15 minutes. A page should show the holder the window and the tradeoff before committing: a longer window is easier for the guardian and widens the exposure of a copied QR by the same amount. Configs already committed keep their window, since the commitment fixes it. Code that read `METHOD_AADHAAR_FRESHNESS_WINDOW` as every config's window must read the window from the config. Code that builds `SetupDescription` records of its own must add `aadhaarWindows`.

- 589ee85: Aadhaar enrollment and replies refuse a proof whose issuer key is not the method's trusted key. The Aadhaar `enrollInput` and `signingInput` take an optional `trustedKeys` parameter, named by the new constant `METHOD_AADHAAR_TRUSTED_KEYS_PARAM`. It holds the method module's `Parties.trustedKeys` exactly as the integrator read them with `trustedParties(module)`: an array of exactly one 32-byte hex word. Any other shape throws a `TypeError` naming `trustedKeys`, with the new `METHOD_AADHAAR_TRUSTED_KEYS_MESSAGE`, before any stack call. The word is copied onto the input as `trustedKey`, a bigint, so its case does not matter. After proving, `configFrom` compares the proof's issuer-key input (`pubkeyHash`, public input 0) with it after the nullifier and seed checks, and `replyFrom` does so after the binding and freshness checks and before the local verdict. A mismatch answers the new reply-failure cause `material-untrusted` through the new constant `METHOD_AADHAAR_MATERIAL_UNTRUSTED`: the material proves, but under an issuer key or version the method's module does not trust now, so the page can ask the guardian for a current QR. `REPLY_FAILURE_CAUSES`, and with it `ReplyFailureCause`, `ReplyFailure` and `EnrollFailure`, gains `material-untrusted` directly after `material-rejected`, six causes. A binding or freshness failure stays `material-rejected` and an abort `device-refused`. A proof under the trusted key that the installed stack cannot check locally still answers `not-judged` and is handed on, leaving the chain to judge it. A hand-built input whose `trustedKey` is not a `uint256` bigint is `material-rejected`. Without the parameter every input, config, reply and verdict is unchanged. The comparison runs after proving only, since the SDK does not compute the circuit's hash of the certificate's key.

  Compatibility: an exhaustive switch on `ReplyFailureCause` gains a case, `material-untrusted`. Pass `trustedKeys` from a `trustedParties(module)` read of the Aadhaar method's module made when the step opens, since a word read before the module rotates its key refuses current proofs. Integrations that pass nothing see no change.

- 589ee85: Every client build (`buildSetupClient`, `buildRecoveryClient`, `recoveryAction()` and `build`) now reads the bound action's `MANAGER()` once, from the zero address at the read tag, as its last construction read, after `version()` or after a handed manager reading; the action is the `withRecoveryAction` address, else the descriptor's. An answer naming another manager than the descriptor's refuses with a `KitRefusalError` carrying the new constant `BUILDER_ACTION_MANAGER_MESSAGE`, whatever `withVersionEscape()`, and caches nothing; a revert or an answer that does not decode as one address builds as before, and any other provider rejection propagates. The orchestrator build reads nothing, as before. `validateSetup`, pure and on the setup client, reports such an action as the error `action.manager-mismatch` (subject `action`, values `action`, `manager`, the descriptor's, and `actionManager`, the action's answer, all checksummed), beside any `account.not-deployed`, `action.unsupported` or `action.unaudited`, since the action spends only its own manager's attempts and a setup committed to another one can never execute. The setup client's `validateSetup` and `describeSetup` each make one more `eth_call`, `MANAGER()` at the pinned block, in the same round trip as the action's other reads; `describeSetup` output is unchanged. New: the constant `RECOVERY_ACTION_MANAGER_ABI`, the error code `action.manager-mismatch` in `SETUP_ERROR_CODES`, after `account.not-deployed`, and the member `ActionReads.manager`, a `ReadResult<Address>`.

  Breaking: `ActionReads` gains the required member `manager`, so a caller of the pure `validateSetup` or `describeSetup` with its own reads must supply it (`{ answered: false }` where it read nothing); both throw a `TypeError` where it is missing or malformed.

  Compatibility: a build over a descriptor or `withRecoveryAction` address whose action answers `MANAGER()` with another manager, which used to succeed, now refuses; such a setup can never execute, so commit again under a matching pair. The closed set `SETUP_ERROR_CODES`, and with it the `ErrorCode` union, grew by one member, so a consumer that keeps an exhaustive map or switch over every error code must add `action.manager-mismatch` before it compiles again; a consumer that reads findings as data is unaffected.

- 589ee85: The encrypted backup's key now takes a PBKDF2 salt bound to the setup. `sealBackup` writes payload version 2 only: its key is derived over the 160-byte associated data of the five authenticated values (account, action, setup commitment, setup nonce and payload version), the same bytes AES-GCM authenticates, so two setups sealed under one password get two keys; after its other checks and before deriving a key it throws a `RangeError` for any `authenticated.payloadVersion` other than `BACKUP_PAYLOAD_VERSION`. `openBackup` keeps its signature and opens the version `authenticated.payloadVersion` names, version 2 keyed over the associated data and version 1 over the zero-length salt; after the 2501-byte length check it refuses any other version with `BackupUnopenedError`, before deriving a key. `restoreConfiguration`, and with it the setup client's `getSetup` and the recovery client's `initRecoveryGathering` and `initCancelGathering` under a password source, open the current setup's backup as version 2 and then as version 1, moving on only on a `BackupUnopenedError`; a payload that opens under neither refuses with one `restore.backup-unopened` whose `authenticated` carries the version-2 values, and any other error rejects as before. The setup client's `prepareCommitSetup` seals version 2 through the constant. Changed: `BACKUP_PAYLOAD_VERSION` is now 2. New: the constants `BACKUP_LEGACY_PAYLOAD_VERSION` (1, opened, never written) and `BACKUP_READ_PAYLOAD_VERSIONS` (`[2, 1]`, the order a restore tries). The payload size, layout, padding, cipher, nonce, associated data, messages, restore codes and records, and every signature are unchanged; no closed set or frozen record changes.

  Breaking: encrypted backups are now sealed as payload version 2, whose PBKDF2-HMAC-SHA256 key (600,000 iterations, unchanged) takes the 160-byte associated data of the five authenticated values as its salt instead of a zero-length salt, so one password no longer gives one key for every account and setup. `BACKUP_PAYLOAD_VERSION` is now 2. `sealBackup` throws a RangeError for any other `payloadVersion`. `openBackup` still opens version-1 payloads under `payloadVersion: 1` and refuses any version but 1 and 2 before deriving a key. `getSetup` and the recovery client's restore try version 2, then version 1, so a wrong password costs two key derivations, and `restore.backup-unopened` reports the version-2 values. Size (2501 bytes), layout, padding and cipher are unchanged. A reader of its own must add the salted derivation. New: `BACKUP_LEGACY_PAYLOAD_VERSION`, `BACKUP_READ_PAYLOAD_VERSIONS`.

  Compatibility: backups already on chain stay readable, with no end date set: a restore opens a version-1 payload through its second attempt with nothing asked of the holder, and `openBackup` opens one under `payloadVersion: BACKUP_LEGACY_PAYLOAD_VERSION`. A holder's version-1 backup stays its rebuild source until it commits a setup again, whose backup is sealed as version 2. A caller of `sealBackup` that passes `BACKUP_PAYLOAD_VERSION` needs no change; one that passes the literal 1 must pass the constant. A caller of `openBackup` with its own values passes the version the payload was sealed under, or tries `BACKUP_READ_PAYLOAD_VERSIONS` in order as the restore does. A payload of the wrong length still costs no key derivation.
