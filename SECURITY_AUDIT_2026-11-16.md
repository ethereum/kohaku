# Kohaku Tornado Cash and Privacy Pools v1 SDK security audit

**Snapshot:** `master` at `706355156b1a4662738fad4f961aabed2f7f1d9d` (`2026-11-16`).  
**Scope:** `packages/tornado-cash`, `packages/privacy-pools`, and the relevant local host, provider, Merkle-tree, Poseidon, and paymaster code. `../kohaku-cli` at `feat/v0.1.9` / `0333143666be7f23040d467fd12d2a848d8e34a5` was used to test how a consumer invokes these SDKs; its Railgun code was excluded.  
**Status:** Findings only. No SDK or CLI fixes were made.

## Executive assessment

The most urgent boundary is **paymaster withdrawal preparation**. Both SDKs sign a complete, potentially executable ERC-4337 UserOperation and send it to the configured bundler as part of gas estimation. An untrusted bundler can submit that operation before the caller calls `broadcast()`, even when a CLI user selects a dry run or later declines confirmation. The signed proof fixes the recipient and fee, so this is an unauthorized *timing and execution* problem, not a claim that the bundler can redirect funds.

The second direct value risk is a permitted but unsafe account configuration: a random delegation sender paired with caller supplied tail calls can pay the withdrawal into an account whose key the SDK immediately discards. An empty tail-call callback is sufficient. The API does not reject the combination, although the README warns about random senders.

The other findings cluster around **completeness of local state** and **amount interpretation**. Privacy Pools verifies that a supplied ASP tree has the on-chain root, but a one-leaf tree containing that root passes the check while omitting every approved label. Its sync also retains orphaned leaves across reorgs and routes exits to the first pool registered for an asset, which breaks after an allowed pool replacement. Tornado can miss valid notes beyond its signature-nonce scan gap or when an external historical event source omits logs; its `0n` withdrawal amount means “all notes.” Several smaller issues expose note material in errors, silently under-shield requested amounts, or obscure partial broadcast failures.

No finding below asserts a bug in the on-chain Tornado or 0xBow contracts. Where contract behavior matters, this audit uses the published upstream source as a model and states the deployed-code assumption. It did not compare live deployed bytecode, run funded mainnet transactions, or audit the prover circuits, contracts, third-party relayers, ASP server, bundler, or upstream npm packages.

### Severity and evidence

**High** means a feasible use of the public SDK API can cause an irreversible withdrawal or leave principal at an inaccessible account. **Medium** means substantial privacy loss, wrong-amount behavior, prolonged inability to use a funded note, or sensitive-data exposure under stated conditions. **Low** means avoidable gas loss or operational confusion without a demonstrated direct loss of principal. “Reproduced” means a focused no-edit runtime probe or existing test exercised the key behavior; “code-confirmed” means the exact branch and downstream calls were traced. Neither is a funded live-chain exploit.

## 1. SDK and dependency map

### Shared host and cryptographic dependencies

The host supplies chain RPC, network transport, storage, keystore, and an optional external event source through [`packages/plugins/src/host/index.ts`](packages/plugins/src/host/index.ts). Each plugin scopes the keystore to its own protocol subtree and explicitly named delegation paths using [`scopeKeystore`](packages/plugins/src/host/scoped-keystore.ts). [`@kohaku-eth/provider`](packages/provider/src/provider.ts) adapts viem or ethers clients into the reads and transactions needed by both SDKs. These host services are security boundaries: provider and event data determine local state, the network sends proof and paymaster requests, and storage saves sync cursors. The CLI uses encrypted per-protocol storage and configures RPC, network, and optional Saga data sources in `../kohaku-cli/src/host/makeHost.ts` and `src/utils/plugins.ts`.

Tornado uses [`@kohaku-eth/mimc-tree`](packages/mimc-tree/src/MimcMerkleTree.ts) for its classic fixed-depth deposit tree and Pedersen-based commitments/nullifiers. Privacy Pools uses [`@kohaku-eth/poseidon-lean-imt`](packages/poseidon-lean-imt/src/limt.ts) for state and ASP lean Merkle trees, with proof building in [`proof.util.ts`](packages/privacy-pools/src/utils/proof.util.ts). The tree root is meaningful for membership, but by itself does not commit to the *number or level* of leaves supplied to a wallet (F-03). Prover artifacts and their integrity checks are relevant: Tornado pins downloaded circuit artifacts before using them; this audit did not find a basis to report arbitrary artifact substitution as a vulnerability.

### Tornado Cash: precise operation flow

1. **Instantiate and sync.** [`createTCPlugin`](packages/tornado-cash/src/v1/factory.ts) constructs [`TornadoCashProtocol`](packages/tornado-cash/src/plugin/base.ts), a worker-backed state manager, `SyncService`, scoped secret manager, relayer client, and optional paymaster client. [`syncThunk`](packages/tornado-cash/src/state/thunks/syncThunk.ts) discovers registry pools, obtains deposit/withdraw events per pool through [`SyncService`](packages/tornado-cash/src/data/sync.service.ts), derives owned secrets, optionally verifies roots, and persists state. Ordinary sync defaults `verify` to false. The external source, when configured for large ranges, supplies both logs and a coverage block; RPC scans only the tail after that block. The CLI constructs separate legacy and signature scanners and may enable Saga history.
2. **Discover balances.** The plugin matches on-chain commitments to either imported classic bearer notes, sequential legacy key derivation, or signature-derived secrets. Signature discovery increments one nonce across pools until 20 consecutive misses ([`discoverUserEventsThunk.ts`](packages/tornado-cash/src/state/thunks/discoverUserEventsThunk.ts)). A balance is an aggregation of discovered, unspent denomination notes, not a contract account balance.
3. **Prepare shield.** [`prepareShield`](packages/tornado-cash/src/plugin/base.ts) syncs, selects catalogued denomination pools, derives a signature-nonce commitment per note, and returns native deposit calls or ERC20 approve/deposit calls from [`getDepositPayloadThunk.ts`](packages/tornado-cash/src/state/thunks/getDepositPayloadThunk.ts). The caller signs and sends those public transactions. Prepared nonces are not reserved in persistent state; only subsequently discovered on-chain notes advance the next nonce.
4. **Prepare relayer unshield.** [`prepareUnshield`](packages/tornado-cash/src/plugin/base.ts) passes the requested asset/amount to the note selector. [`withdrawThunk.ts`](packages/tornado-cash/src/state/thunks/withdrawThunk.ts) verifies relevant roots on-chain, selects a relayer and a fee, and proves each selected note. Stake is checked when relayers are first registered in local state, but cached relayers are not rechecked on every quote. The Groth16 public inputs bind root, nullifier hash, recipient, relayer, fee, and refund, following the [published Tornado core contract](https://github.com/tornadocash/tornado-core/blob/master/contracts/Tornado.sol). [`TCBroadcaster`](packages/tornado-cash/src/plugin/broadcaster.ts) sends proofs to relayer HTTP endpoints; it catches individual failures (F-13).
5. **Prepare paymaster unshield.** [`paymasterWithdrawThunk.ts`](packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts) chooses the first note to sponsor gas with a paymaster-bound proof. A single note without tail calls pays the requested recipient directly with zero execution gas. Extra notes in a batch withdraw to a shared execution sender; without tail calls the SDK builds a forward, while caller tail calls replace that forward. It derives or accepts the execution account, constructs an EIP-7702/smart-account UserOperation, signs it, estimates/refines gas through the bundler, then returns the operation. The paymaster broadcaster later submits the signed operation and waits. The estimate call is already a disclosure of a potentially executable operation (F-01).

### Privacy Pools v1: precise operation flow

1. **Instantiate and sync.** [`createPPv1Plugin`](packages/privacy-pools/src/v1/factory.ts) constructs [`PrivacyPoolsV1Protocol`](packages/privacy-pools/src/plugin/base.ts), a scoped signature-derived secret manager by default, state manager, ASP client, relayer client, prover, and data service. The CLI chooses signature or legacy derivation explicitly, uses OxBow's ASP endpoint, and uses Saga event history on mainnet (`../kohaku-cli/src/utils/plugins.ts`). [`syncThunk.ts`](packages/privacy-pools/src/state/thunks/syncThunk.ts) pins one head; scans Entrypoint deposits, ASP root updates and pool lifecycle events; scans every known pool for deposits, withdrawals, ragequits and leaf insertions; downloads the ASP tree; rebuilds roots; and checks them on-chain. Public chain state is shared, while account secret discovery runs afterward. A successful sync publishes/persists the state and cursor; a failed one leaves in-memory reducer mutations pending ([`chain-state.ts`](packages/privacy-pools/src/state/chain-state.ts)).
2. **Discover notes and approvals.** Signature derivation signs a chain/entrypoint-bound envelope and derives deposit/withdrawal-indexed nullifiers and secrets ([`signature-keys.ts`](packages/privacy-pools/src/account/signature-keys.ts)); the legacy scheme uses HD keys. [`discoverUserSecretsThunk.ts`](packages/privacy-pools/src/state/thunks/discoverUserSecretsThunk.ts) scans sequential deposit indices and then tracks change notes. Entrypoint events map a commitment to its actual pool/asset; pool withdrawal events reduce balance. ASP leaf membership determines the SDK's approved/pending status. The public `INote` drops the actual pool address, which matters after a replacement (F-04).
3. **Prepare shield.** [`prepareShield`](packages/privacy-pools/src/plugin/base.ts) syncs, derives the next precommitment from the count of discovered deposits ([`state-manager.ts`](packages/privacy-pools/src/state/state-manager.ts)), and returns an Entrypoint native/ERC20 deposit transaction. The chain's current asset config directs it to a pool, takes the vetting fee, and emits the events that later associate the note with a pool. The caller sends the public transaction.
4. **Prepare relayer unshield.** The SDK selects an approved note, requests a relayer quote, verifies the quote's canonical withdrawal data/recipient/fee against quoted and contract bounds, and makes a withdrawal context bound to that data ([`quoteThunk.ts`](packages/privacy-pools/src/state/thunks/quoteThunk.ts), [`state-manager.ts`](packages/privacy-pools/src/state/state-manager.ts)). [`withdrawThunk.ts`](packages/privacy-pools/src/state/thunks/withdrawThunk.ts) derives change-note secrets, obtains the pool-state and ASP inclusion paths, requires an ASP root verified against Entrypoint `latestRoot()` in this session, and proves a withdrawal. The broadcaster sends proof/quote to the chosen relayer. Exact-output mode sizes gross withdrawal and checks the recipient's net; amount obfuscation is opt-in.
5. **Prepare paymaster unshield.** [`paymasterWithdrawThunk.ts`](packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts) spends one note as the gas sponsor and optionally additional notes in the execution phase. It quotes gas/fee, selects a derived/external/random sender, preflights account state, proves the sponsoring withdrawal to either the recipient or sender, builds the forward/tail calls, signs the UserOperation, and asks the bundler to estimate it. Exact-output paymaster mode requires an explicit refund recipient. [`PaymasterBroadcaster`](packages/privacy-pools/src/paymaster/paymaster-broadcaster.ts) later submits and waits. F-01 and F-02 apply here too.
6. **Public ragequit.** [`ragequit`](packages/privacy-pools/src/plugin/base.ts) syncs without requiring the ASP service and proves the current commitment directly against the pool. The published [0xBow v1 PrivacyPool contract](https://github.com/0xbow-io/privacy-pools-core/blob/main/packages/contracts/src/contracts/PrivacyPool.sol) requires the original depositor for the note's label and does not require ASP membership; an approved note can also ragequit, but the public exit reveals the deposit link. Change notes retain that label, so their original depositor can generally ragequit them too. A note holder who differs from the original depositor or lacks that wallet cannot use this route alone. The CLI adds its own policy that blocks approved notes and warns before public ragequit.

## 2. Detailed findings

### F-01 — High — A signed paymaster withdrawal can be submitted during “prepare”

**What happens.** Preparing a paymaster withdrawal sends a fully signed, proof-bearing UserOperation to the configured bundler for gas estimation. The bundler can submit that same operation to an EntryPoint without a later SDK `broadcast()` call. The caller's intended dry run or final confirmation therefore does not control execution once estimation begins.

**Path and proof.** Tornado builds a signed operation in [`paymasterWithdrawThunk.ts:293-330`](packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts#L293), then its estimation loop builds *before* calling the estimator in [`estimate.ts:37-46`](packages/tornado-cash/src/paymaster/estimate.ts#L37). [`utils.ts:203-211`](packages/tornado-cash/src/paymaster/utils.ts#L203) sends the serialized operation as an `eth_estimateUserOperationGas` parameter. The operation includes the proof, paymaster data, signature, and potentially EIP-7702 authorization ([`utils.ts:273-325`](packages/tornado-cash/src/paymaster/utils.ts#L273)). Privacy Pools does the equivalent in [`paymasterWithdrawThunk.ts:269-315`](packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L269) and [`paymaster/utils.ts:125-138`](packages/privacy-pools/src/paymaster/utils.ts#L125). An existing Tornado unit test asserts that a final signed operation reaches the estimator (`tests/unit/paymaster-withdraw-estimation.test.ts:213-219`). The CLI calls preparation first, labels output “not broadcast” and “dry run” without `--broadcast`, and asks for user confirmation only afterward (`../kohaku-cli/src/commands/unshield.ts:1584-1626,1776-1850,1885-1920`).

**Conditions and impact.** The configured bundler (or a party able to replace its response path) must act maliciously, and one of the disclosed provisional/final operations must have sufficient gas and otherwise be valid. A rejected simulation does not by itself prove validity. If valid, the bundler can consume the note, fee, and nonce, reveal the recipient/nullifier relationship at a time the user did not approve, and make the later intended broadcast fail as already spent. The proof and signature bind the destination; there is no demonstrated ability to redirect the principal to the bundler. This affects both SDK callers and the CLI's dry-run/confirmation semantics, including the default public bundler configuration in each SDK.

**Remediation direction.** Treat signed UserOperations as executable bearer transactions. Estimate with an unsigned simulation shape or trusted local simulation, and sign only after final user consent; document any remaining bundler disclosure. Verify the signed final operation's gas and fee without transmitting it to an untrusted party before authorization.

### F-02 — High — Random sender plus tail calls can leave principal at an inaccessible account

**What happens.** A random delegation mode creates a fresh private key, returns only the account object internally, and never persists or exposes that key. When caller-supplied tail calls enable an execution phase, the sponsoring withdrawal pays the account itself. Supplying `tailCalls: async () => []` suppresses the SDK's automatic forward to the requested recipient. If the UserOperation executes, the withdrawn value remains at an address for which the caller has no signing key.

**Path and proof.** Tornado sets `validationOnly = false` whenever `tailCalls` is supplied, including an empty callback ([`paymasterWithdrawThunk.ts:99-104`](packages/tornado-cash/src/state/thunks/paymasterWithdrawThunk.ts#L99)). It creates and discards the random key at `:197-208`, pays the first note to the sender at `:325`, and uses *either* caller tail calls *or* synthesized forwarding at `:286-291`. Privacy Pools similarly sets `hasExecutionPhase` at [`paymasterWithdrawThunk.ts:139-140`](packages/privacy-pools/src/state/thunks/paymasterWithdrawThunk.ts#L139), pays the sender at `:187-195`, replaces forwarding with the callback at `:256-260`, and creates a nonpersisted random signer at `:383-395`. Existing Tornado tests cover the random mode and empty-callback execution branch (`tests/unit/paymaster-withdraw-estimation.test.ts:265-274,561-571`). The SDK README warns random senders can strand funds; the API still accepts this configuration.

**Conditions and impact.** The caller must select `delegation.mode: 'random'` and an execution phase (tail calls or a multi-note batch). The direct empty-callback example is a deterministic way to create no forwarding call. For a successful operation, the recipient does not receive the requested payout and the sender has no recoverable key through the SDK. A failed execution in a batch can also leave any validation-phase payout at that sender. This is a caller/API safety issue, not an adversary stealing to its own address. The illustrative CLI uses recoverable execution accounts instead.

**Remediation direction.** Reject random sender configurations that can receive principal, or ensure every successful path forwards and that any residual value has a recoverable owner. Use a deterministic or externally controlled sender for batch and custom execution flows.

### F-03 — Medium — A forged ASP tree can pass root verification while hiding every approval

**What happens.** Privacy Pools rebuilds the ASP Merkle root from the first array of leaves returned by the ASP service and compares it to the Entrypoint `RootUpdated` value. In a lean tree, a one-leaf tree's root is the leaf itself. If the legitimate root is `R`, a malicious ASP gateway can return `[[R]]`. The SDK accepts this as the current tree and verifies it against on-chain `latestRoot()`, although none of the actual approved labels is present.

**Path and proof.** [`syncAspThunk.ts:21-46`](packages/privacy-pools/src/state/thunks/syncAspThunk.ts#L21) documents the ambiguity and checks only field range and rebuilt root. [`poseidon-lean-imt/src/limt.ts:52-54,96-119`](packages/poseidon-lean-imt/src/limt.ts#L52) implements the one-leaf behavior. [`verifyRootsThunk.ts:27-60`](packages/privacy-pools/src/state/thunks/verifyRootsThunk.ts#L27) marks that same `R` verified on-chain. [`isAspTreeCurrent`](packages/privacy-pools/src/state/thunks/syncAspThunk.ts#L54) then accepts the stored tree until a new root event; [`myDepositsSelector`](packages/privacy-pools/src/state/selectors/deposits.selector.ts#L16) marks genuine labels pending and the ASP proof builder cannot find them. A no-edit runtime probe used genuine leaves `[10,20,30,40,50]`, built `R`, substituted `[R]`, and observed equal roots; actual `syncAspThunk` and `verifyRootsThunk` accepted `[R]`, while a proof for label `20` failed with `Leaf not found`.

**Conditions and impact.** An ASP service or gateway response must be malicious or corrupted. The genuine ASP tree must contain more than this single fake leaf. The attacker can selectively or wholly censor private exits and misreport approval while the on-chain root check appears green. The note's original depositor can generally make a public ragequit under the published v1 contract, including for a change note with the same label, but that reveals the deposit link; a different note holder may not control the required depositor address. The CLI's `ragequit` policy blocks notes it *believes* approved, so this false pending state can also steer an informed user toward the public exit, with a warning. This is not a demonstrated ability to steal principal or to alter the contract's real ASP membership.

**Remediation direction.** Authenticate the canonical ASP leaf list or bind its count/shape to an independently trusted checkpoint. A root-only check cannot distinguish a higher-level node from original leaves; warn or fail closed when membership data cannot be authenticated.

### F-04 — Medium — Replacing a pool for an asset breaks SDK exits from the new pool

**What happens.** The Privacy Pools SDK records multiple pools for the same asset but chooses the *first* one for withdrawals and ragequits. After an allowed remove/register lifecycle replaces pool A with pool B, new deposits go to B and can appear in balances, but proof generation and broadcast still use A's address/scope/adapter. New notes cannot be exited correctly through the SDK's normal paths.

**Path and proof.** [`pools.selector.ts:117-133`](packages/privacy-pools/src/state/selectors/pools.selector.ts#L117) uses `Array.from(pools).find` by asset; [`poolsSlice.ts:22-31`](packages/privacy-pools/src/state/slices/poolsSlice.ts#L22) preserves insertion order. `INote` omits the actual pool address in [`notes.selector.ts:100-117`](packages/privacy-pools/src/state/selectors/notes.selector.ts#L100), although balances join the Entrypoint deposit's real `poolAddress` in [`balance.selector.ts:15-32`](packages/privacy-pools/src/state/selectors/balance.selector.ts#L15). Relayer, paymaster, and ragequit paths call the asset-only selector (`state-manager.ts:392,452`; `withdrawThunk.ts:60-70`; `paymasterWithdrawThunk.ts:119-126`; `ragequitThunk.ts:42-45`). Further, [`syncPoolsThunk.ts:17-36`](packages/privacy-pools/src/state/thunks/syncPoolsThunk.ts#L17) applies a wind-down only if its registration appears in the *same sync batch*, so a later wind-down is dropped; `syncThunk` does not subscribe to `PoolRemoved`. A no-edit runtime probe registered A for asset 42, processed A's wind-down in a later sync, then registered B for asset 42: lookup still returned A with `woundDownAtBlock: null`.

**Conditions and impact.** The Entrypoint owner must actually remove and replace a pool. The published [0xBow v1 Entrypoint source](https://github.com/0xbow-io/privacy-pools-core/blob/main/packages/contracts/src/contracts/Entrypoint.sol) permits that lifecycle; this audit did not establish that it has happened on the user's deployment. New B notes fail membership/context or target the wrong address. A mixed A/B batch is also invalid. Old notes require routing to A, so simply switching the asset lookup to “latest” is insufficient. This is an SDK availability failure; manual contract interaction or migration-specific recovery may remain possible.

**Remediation direction.** Preserve the deposit's actual pool address and scope with each note and route proof/exit per note. Process lifecycle events independently and reconcile the current asset mapping with the Entrypoint's on-chain config.

### F-05 — Medium — Incomplete historical event streams can hide funded notes after cursor advancement

**What happens.** Event-source coverage is treated as completeness. If a configured external source claims a range while omitting a deposit, withdrawal, leaf, or Entrypoint event, the SDK can advance its cursor beyond the omission. A later healthy source then starts after it and cannot recover the missing note by ordinary sync.

**Tornado path.** [`SyncService.getPoolEvents`](packages/tornado-cash/src/data/sync.service.ts#L35) accepts `lastCoveredBlock` and raw events from a host external provider, then asks RPC only for `coverage + 1` onward (`:137-178`). [`syncEventsThunk.ts:35-79`](packages/tornado-cash/src/state/thunks/syncEventsThunk.ts#L35) stores the returned per-pool `toBlock`; ordinary [`syncThunk.ts:25-50`](packages/tornado-cash/src/state/thunks/syncThunk.ts#L25) defaults root verification off. Even when explicit verification runs, a pool with no local leaves is skipped ([`verifyRootsThunk.ts:28-39`](packages/tornado-cash/src/state/thunks/verifyRootsThunk.ts#L28)). An omitted funded commitment is absent from note discovery but the scan cursor says it is covered. The CLI can configure Saga as this source.

**Privacy Pools path.** [`DataService`](packages/privacy-pools/src/data/data.service.ts#L43) accepts an alternate `getLogs`, and [`createSagaLogSource`](packages/privacy-pools/src/data/saga-log-source.ts#L90) can synthesize `LeafInserted` from published events. [`syncThunk.ts:35-101`](packages/privacy-pools/src/state/thunks/syncThunk.ts#L35) advances to a pinned head on successful verification. [`verifyRootsThunk.ts:37-45`](packages/privacy-pools/src/state/thunks/verifyRootsThunk.ts#L37) skips a pool with zero local leaves; a direct thunk probe confirmed that an on-chain nonzero pool root was never queried when no local leaves were present. For a nonempty but incomplete prefix, [`verifyStateRootOnChain`](packages/privacy-pools/src/verification/root-verification.ts#L53) accepts a root in the pool's previous 64 roots. That proves the local prefix once existed; it does **not** prove the event stream covers the pinned head. The comment in `saga-log-source.ts:97-103` says the rebuilt tree must match `currentRoot()`, but the implementation accepts a historical root. The illustrative CLI's mainnet path uses Saga logs. In a no-edit `syncThunk` probe, pool leaf `77` established root `R1`; the source withheld later leaf `88` while chain root advanced to `R2`; the verifier accepted historical `R1` and advanced the cursor. After two more successful syncs and source repair, the SDK still had only leaf `77` because the cursor had passed the omitted block. A single omission in the most recent block may recover through the inclusive replay; the probe kept it omitted until the cursor passed that block.

**Conditions and impact.** The external provider/CDN must be incomplete or malicious, or a configured RPC/log source must omit logs while claiming the queried range. This is a source trust issue, not arbitrary on-chain fund transfer. A missing deposit can disappear from balances and note selection indefinitely; a missing withdrawal can show a false balance. The owner may have to reset/rebuild state from a complete source. Signed Saga manifests, where present, authenticate the publisher rather than proving the publisher's event set complete.

**Remediation direction.** Bind sync cursors to a verified head and validate event completeness against authoritative chain checkpoints or periodically rescan a finality window. For Privacy Pools, distinguish “root is accepted for proof submission” from “local event stream is complete through head.”

### F-06 — Medium — Reorged events are never removed from local state

**What happens.** Both SDKs merge newly fetched events into persistent maps but have no block-hash checkpoint or rollback of events that disappeared from the canonical chain. After a reorg, a state tree may contain orphaned leaves, or a valid note may remain marked spent because an orphaned withdrawal is still recorded.

**Path and proof.** Privacy Pools scans forward from [`lastSyncedBlock`](packages/privacy-pools/src/state/thunks/syncEventsThunk.ts#L29) and only appends/upserts leaves and events (`:59-85`); [`poolLeavesSlice.ts:34-49`](packages/privacy-pools/src/state/slices/poolLeavesSlice.ts#L34) never removes a leaf. [`syncThunk.ts:35-40,98-101`](packages/privacy-pools/src/state/thunks/syncThunk.ts#L35) stores a block number but no canonical hash. A no-edit runtime probe synced leaf `77` at cursor block `2` with on-chain root `77`, simulated a canonical reorg that removed it and changed the root to `0`, then ran sync twice: both attempts failed state-root verification against retained `77`, leaving normal operations unable to progress until local state is rebuilt. A failed sync does not publish the unverified state, which limits false reporting but does not repair the reducer state. Tornado likewise scans from stored per-pool blocks ([`syncEventsThunk.ts:30-41`](packages/tornado-cash/src/state/thunks/syncEventsThunk.ts#L30)) and only upserts deposits/withdrawals ([`depositsSlice.ts:22-42`](packages/tornado-cash/src/state/slices/depositsSlice.ts#L22), [`withdrawalsSlice.ts:22-31`](packages/tornado-cash/src/state/slices/withdrawalsSlice.ts#L22)); its tree selector orders every retained commitment by leaf index, and a conflicting replacement produces a root that fails on-chain verification. The Tornado scenario is code-confirmed rather than runtime-probed.

**Conditions and impact.** A chain reorg must affect already synced events, including events in the most recent scanned block; a malicious source that rewrites its history can create a similar condition. Root checks block an invalid withdrawal proof, but they do not restore a correct balance or usable local tree. A user may need to delete local chain state or perform a full rescan. This is availability and accounting integrity, not proven on-chain loss of funds.

**Remediation direction.** Sync only finalized blocks or keep a rolling overlap with block-hash/reorg detection and state rollback. Make recovery automatic when canonical history diverges.

### F-07 — Medium — Tornado `amount: 0n` means full-balance withdrawal

**What happens.** The public Tornado API accepts `assets.amount` and forwards it unchanged. The selector uses truthiness checks (`if (amount)`) rather than checking whether the value is defined or positive. `0n` therefore disables every amount bound, selecting all available notes.

**Path and proof.** [`base.ts:303-333`](packages/tornado-cash/src/plugin/base.ts#L303) passes the amount to both relayer and paymaster preparation. [`withdrawals.selector.ts:94-140`](packages/tornado-cash/src/state/selectors/withdrawals.selector.ts#L94) tests `amount` at the overshoot and insufficiency branches. A direct no-edit selector probe with five notes totaling 22 units found: `undefined` selected all five, `0n` selected all five, and `10n` selected the single 10-unit note. Both withdrawal modes then prove the selected notes. The illustrative CLI rejects nonpositive amounts (`../kohaku-cli/src/lib/unshield-flow.ts:373-394`), so the issue primarily affects SDK consumers or wrappers that use zero as a sentinel.

**Conditions and impact.** A caller must pass `0n`, expecting no-op or validation failure. If the resulting operation is broadcast, every selected note is withdrawn and pays any associated fees, with a potentially much larger public recipient transfer and privacy effect than requested. In paymaster mode, F-01 means a malicious bundler may be able to act after estimation. The proof still binds the configured recipient.

**Remediation direction.** Reject zero/negative explicit amounts at the public boundary. Use `amount !== undefined` for denomination selection and make “all” an explicit operation.

### F-08 — Medium — The 20-nonce discovery gap can hide a funded Tornado note

**What happens.** Signature-note discovery stops after 20 consecutive nonce values that have no matching deposit in any active pool. Shield preparation assigns sequential nonces across a batch but does not reserve prepared notes. If a user broadcasts only a later prepared deposit (or earlier transactions fail), a funded high-nonce note can sit beyond the scan gap and remain absent from balance and withdrawal selection.

**Path and proof.** [`discoverUserEventsThunk.ts:8-53`](packages/tornado-cash/src/state/thunks/discoverUserEventsThunk.ts#L8) increments `misses` across nonce values and breaks at 20. [`getDepositPayloadThunk.ts:97-129`](packages/tornado-cash/src/state/thunks/getDepositPayloadThunk.ts#L97) assigns `startNonce + i` based on *discovered* notes; it returns transactions without a pending-nonce record. The existing `tests/unit/discover-user-events.test.ts:94-111` demonstrates that a deposit at nonce 20 is found but one at 21 is omitted after the gap. A user can reach nonce 21 by preparing a batch and submitting that transaction while the intervening ones are omitted. The CLI has a separate nonce-allocation helper, which reduces some CLI cases but does not change the SDK behavior.

**Conditions and impact.** At least 20 earlier signature nonces must have no on-chain deposit. The funds remain controlled by derivable secrets; they are not cryptographically lost. Standard sync does not reveal the note, so normal SDK withdrawal cannot select it without custom scan/recovery or filling earlier nonces.

**Remediation direction.** Persist prepared nonce reservations or expose bounded recovery scanning beyond the gap. Never let a successfully prepared deposit index become permanently undiscoverable solely because prior prepared transactions were skipped.

### F-09 — Medium — Malformed legacy-note errors print the whole bearer secret

**What happens.** Tornado's legacy note parser interpolates the complete submitted note into errors for invalid grammar and wrong preimage length. A near-valid funded bearer note with a typo can therefore appear in terminal logs, crash reports, or telemetry. Anyone who receives its intact 62-byte preimage may be able to spend the note.

**Path and proof.** [`parseLegacyNote`](packages/tornado-cash/src/account/legacyNote.ts#L25) throws `Invalid tornado cash note: ${note}` or `Invalid tornado cash note preimage length: ${note}` at lines 29 and 36. [`importLegacyNotesThunk.ts:29-30`](packages/tornado-cash/src/state/thunks/importLegacyNotesThunk.ts#L29) propagates it; the illustrative CLI prints the caught error (`../kohaku-cli/src/commands/import-tornado-note.ts:236-237`). Whether the actual typo leaves a still-spendable preimage depends on which part was malformed; exposing a correct preimage with a malformed prefix/denomination is enough.

**Conditions and impact.** The user must import a malformed note, and another person/system must receive the error output. This is a secret-exposure path, not an automatic leak on successful normal import. The CLI also prints raw successfully imported notes in noninteractive JSON; see the appendix.

**Remediation direction.** Never interpolate note text or preimage into errors. Identify the invalid field without echoing its value, and audit CLI/logging paths for bearer-note redaction.

### F-10 — Medium — Tornado estimation errors retain the signed operation in `cause`

**What happens.** When bundler gas estimation fails, Tornado wraps the viem error with `{ cause }`. The package's own paymaster utility notes that viem errors can embed the signed UserOperation request body and should not be attached as a cause. Error collectors that recursively serialize causes can leak proof, nullifier, recipient, signature, and authorization material.

**Path and proof.** The estimator sends the signed operation in [`paymaster/utils.ts:203-211`](packages/tornado-cash/src/paymaster/utils.ts#L203). The warning and `describeError` helper are at [`utils.ts:114-123`](packages/tornado-cash/src/paymaster/utils.ts#L114). [`estimate.ts:45-49,88`](packages/tornado-cash/src/paymaster/estimate.ts#L45) extracts a short message but still rethrows the original object as `cause`. Privacy Pools instead converts its viem error to a new short message at [`paymaster/utils.ts:133-140`](packages/privacy-pools/src/paymaster/utils.ts#L133).

**Conditions and impact.** Estimation must fail and an integrator's logging/crash reporter must traverse causes; plain `JSON.stringify(new Error(...))` usually will not. The proof is not itself a note secret, but it links transaction metadata and includes an executable signed operation (F-01). This is a privacy and transaction-control leak conditional on telemetry.

**Remediation direction.** Drop the original cause at this boundary and keep only allowlisted, redacted error fields; test the actual logger/telemetry serialization used by consumers.

### F-11 — Medium — Tornado shield requests can silently deposit less than requested

**What happens.** Shield preparation decomposes a requested amount into whole denomination pools, floors any remainder, and returns successfully even when the transaction list is empty. A consumer that displays or records the input amount as shielded can leave a meaningful balance in the public wallet without an error.

**Path and proof.** [`calculatePoolsDeposits`](packages/tornado-cash/src/state/thunks/getDepositPayloadThunk.ts#L30) divides by pool denomination under both strategies (`:51,63`) and never checks the remaining amount. [`getDepositPayloadThunk.ts:112-168`](packages/tornado-cash/src/state/thunks/getDepositPayloadThunk.ts#L112) builds only that many transactions. A no-edit thunk probe with an available 0.1 ETH pool confirmed that 0.15 ETH produces one 0.1 ETH deposit, while 0.05 ETH produces an empty successful payload. The plugin returns it as a prepared public operation. The CLI validates exact denomination coverage in its own flow; direct SDK users must do so themselves.

**Conditions and impact.** The caller must request an amount that is not exactly representable by available pools and fail to reconcile the returned transactions with the input. This does not transfer the remainder away; it leaves it public and may mislead accounting or privacy UI. The impact is particularly material where a wallet promises the entire requested amount is shielded.

**Remediation direction.** Make the credited/shielded amount explicit and reject unrepresentable requests unless the caller opts into partial shielding.

### F-12 — Low — Greedy Tornado note selection can reject a feasible spend

**What happens.** The withdrawal selector iterates denomination pools from largest to smallest, takes notes that fit, and never backtracks. A large note can block a combination of smaller notes that exactly meets the requested amount.

**Path and proof.** [`withdrawals.selector.ts:102-140`](packages/tornado-cash/src/state/selectors/withdrawals.selector.ts#L102) sorts descending and skips an overshooting note without reconsidering earlier choices. A direct selector probe with holdings `10 + 3 + 3 + 3 + 3` and request `12` returned insufficient balance after selecting `10`, although four `3` notes cover `12`. Extended Tornado ETH denominations include 1 and 0.3 ETH, so the same pattern can occur with `1 + 0.3 + 0.3 + 0.3 + 0.3` and a 1.2 ETH request when those pools are enabled. The CLI availability check follows the same greedy approach.

**Conditions and impact.** The user must have a combination of denominations where the largest-first choice blocks an exact subset. No funds are lost; the SDK refuses an otherwise possible private withdrawal and may prompt unnecessary splitting or public transactions.

**Remediation direction.** Use bounded subset-sum selection for denomination notes or surface a clear “available but not selected” outcome.

### F-13 — Low — Tornado relayer broadcast hides per-note failures

**What happens.** Tornado's broadcaster catches each relayer submission failure, prints a warning, and resolves with only successful responses. It resolves `[]` even if all requested notes failed. A caller that treats promise resolution as broadcast success can report completion without having spent the notes.

**Path and proof.** [`broadcastViaRelayer`](packages/tornado-cash/src/plugin/broadcaster.ts#L51) accumulates `failures` but returns `successes` at lines 73-77. With partial success, some notes are irreversibly spent and others are not; the array does not preserve one result per requested note. The illustrative CLI has a generic wrapper that would accept such a result, but its normal Tornado `unshield` command prepares paymaster operations, whose broadcaster checks the response count. The observed false-success path therefore applies directly to SDK relayer consumers, not the normal CLI command.

**Conditions and impact.** A relayer must reject, time out, or fail. The false-success signal is an integration risk and can complicate retry/reconciliation; on-chain nullifiers prevent a second successful spend of the same note. This is not a fund-theft path.

**Remediation direction.** Return one indexed success/failure result per requested proof or throw an aggregate error that includes completed note identifiers.

### F-14 — Low — Two prepared Privacy Pools deposits can reuse one precommitment

**What happens.** `prepareShield` derives its deposit index from already discovered deposits. Two preparations before the first transaction is mined and synced can generate the same precommitment. Submitting both transactions is not a supported way to create two independent notes.

**Path and proof.** [`state-manager.ts:274-286`](packages/privacy-pools/src/state/state-manager.ts#L274) takes `myDepositsCountSelector(state)` and derives the precommitment without reserving it. The published [0xBow v1 Entrypoint source](https://github.com/0xbow-io/privacy-pools-core/blob/main/packages/contracts/src/contracts/Entrypoint.sol) rejects reused precommitments. Thus, assuming deployed-code equivalence, the second transaction reverts and burns gas rather than funding an unrecoverable duplicate note. The illustrative CLI has a nonce helper for its preparation flow, but SDK callers can still trigger this directly.

**Conditions and impact.** The same account prepares multiple shields while earlier ones are pending, then submits both. The consequence is failed second deposit and gas loss; this audit found no basis to claim two funded notes become indistinguishable.

**Remediation direction.** Reserve pending deposit indices transactionally or return an explicit nonce/index for the caller to manage across concurrent preparations.

## 3. CLI observations and consumption model

The CLI matters because it makes the SDK's trust boundary concrete. It constructs protocol plugins with encrypted storage, RPC, network and optional Saga sources; exposes shield, unshield, notes/balance and Privacy Pools ragequit; and offers dry-run/prepare output before optional broadcast. Its paymaster unshield path prepares the signed operation before it asks for broadcast confirmation (F-01). Its Tornado input validation rejects zero amounts and checks representable denominations, reducing F-07 and F-11 for its own commands but leaving the SDK issues intact. It normally uses recoverable execution accounts, reducing F-02 for its commands.

One additional CLI-specific observation is worth carrying into a later CLI review: noninteractive successful legacy-note import includes the raw note in JSON (`../kohaku-cli/src/commands/import-tornado-note.ts:202-214`); scripts that log stdout can preserve bearer secrets. The CLI's normal Tornado unshield path uses the paymaster mode, so F-13's relayer failure behavior is an SDK integration risk rather than a demonstrated CLI command failure. This appendix is illustrative, not a full CLI audit; Railgun was excluded.

## 4. Controls observed and boundaries of the claims

- Both plugins scope secret derivation to their protocol paths. Privacy Pools checks relayer withdrawal data, recipient and fee before proving; it verifies the ASP *root* against on-chain `latestRoot()` for a session. These controls constrain redirection and arbitrary ASP-tree tampering, although they do not establish leaf-list shape or event completeness.
- Tornado proofs bind the recipient, relayer, fee and nullifier; on-chain root/nullifier checks prevent an untrusted relayer from changing those values or replaying a spent note. F-01 is therefore about premature submission of an already authorized payload, and F-13 about failed/partial delivery.
- Privacy Pools pool-state roots may intentionally use the contract's recent-root history so a previously proved withdrawal remains valid. That acceptance is suitable for proof validity but cannot certify that an event stream reached the current sync head (F-05).
- The upstream v1 contracts were consulted for permitted pool replacement, reused precommitments, and ragequit rules. Deployed bytecode equivalence and production configuration were not established. No claim here implies that a given attack has occurred.
- The two high findings require a malicious configured bundler or an unsafe caller-selected delegation mode, respectively. Several medium findings are conditional on external log/ASP misbehavior, a reorg, or particular user inputs; their impact descriptions state those conditions.

## 6. Suggested triage order

1. Resolve F-01's pre-consent signed-operation disclosure in both paymaster flows and align CLI dry-run wording/behavior.
2. Reject or make recoverable F-02's random sender with execution phase; add explicit zero-amount validation for F-07.
3. Address Privacy Pools F-03 ASP leaf-list authenticity and F-04 note-to-pool identity before relying on the SDK through an ASP outage or pool replacement.
4. Make history complete and recoverable across external-source omissions and reorgs (F-05/F-06), then tackle nonce discovery and amount integrity (F-08/F-11).
5. Redact sensitive error/CLI output and report per-note broadcast outcomes (F-09/F-10/F-13); treat F-12/F-14 as correctness hardening.
