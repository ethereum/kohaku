Dev and test modes for the two identity methods, both client-side only: the chain is untouched. `zkPassportMethod({ stack, devMode })` takes an options record, `ZkPassportMethodOptions`; with `devMode: true` the method opens its requests and asks `getSolidityVerifierParameters` in dev mode, refuses a verifier-parameter echo of the other mode as `material-rejected`, and accepts the zkPassport app's fake-passport proofs (nullifier type 2) at `configFrom`, `replyFrom` and `verify` wherever a real document's proof (type 0) is accepted; `verify` still answers `not-judged`. The deployed module verifies with dev mode off and refuses any nullifier type but zero, so a fake-passport reply is rejected on chain. `replyFrom` now also refuses a proof whose nullifier type the mode does not accept. `anonAadhaarMethod({ testMode: true })`, combined with `stack` or `artifacts`, makes the local verdict check the proof against anon-aadhaar's test key, so a test-QR proof answers `satisfied`; the deployed module checks its own trusted key, so such a proof satisfies only a module whose trusted key is the test key's hash. Once the peer is loaded, the default stack compares the proof's `pubkeyHash` with the peer's `testPublicKeyHash` in test mode and its `productionPublicKeyHash` outside it, and answers `rejected` for a proof signed by the other key (a real QR in test mode, a test QR outside it) without calling the peer's `verify`, so `replyFrom` refuses it as `material-rejected` instead of handing it on; `not-judged` stays for a stack that could not load or verify. An injected stack judges keys itself. `AadhaarCoreSurface` declares the two hash members, which the loaded peer must carry. Both modes are off by default.

The zkPassport `configFrom` accepts its proofs from `material.result.proofs` or, where that member is absent (an explicit `null` is refused as a malformed list), from `material.proofs`: the `onResult` payload and the peer's `verify()` result beside the `onSuccess` proofs both enrol. `ZkPassportRequest` declares the peer's `onResult` (deprecated), `onBridgeConnect` and `onBridgeConnectionLost`, and the method's own `cancel()`, which closes the request through the client's `cancelRequest(requestId)`, now declared on `ZkPassportClient`; `ZkPassportRequestArgs.devMode` and the verifier-parameter call's `devMode` are `boolean`.

Breaking: `zkPassportMethod(stack)` becomes `zkPassportMethod({ stack })`; `METHOD_ZKPASSPORT_DEV_MODE` is renamed `METHOD_ZKPASSPORT_DEFAULT_DEV_MODE`; an injected zkPassport stack must now declare `cancelRequest(requestId)` on its client and `onResult`, `onBridgeConnect` and `onBridgeConnectionLost` on the record its `done()` returns, as `@zkpassport/sdk` 0.17.1 does.
