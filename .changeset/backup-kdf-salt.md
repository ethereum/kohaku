The encrypted backup's key now takes a PBKDF2 salt bound to the setup. `sealBackup` writes payload version 2 only: its key is derived over the 160-byte associated data of the five authenticated values (account, action, setup commitment, setup nonce and payload version), the same bytes AES-GCM authenticates, so two setups sealed under one password get two keys; after its other checks and before deriving a key it throws a `RangeError` for any `authenticated.payloadVersion` other than `BACKUP_PAYLOAD_VERSION`. `openBackup` keeps its signature and opens the version `authenticated.payloadVersion` names, version 2 keyed over the associated data and version 1 over the zero-length salt; after the 2501-byte length check it refuses any other version with `BackupUnopenedError`, before deriving a key. `restoreConfiguration`, and with it the setup client's `getSetup` and the recovery client's `initRecoveryGathering` and `initCancelGathering` under a password source, open the current setup's backup as version 2 and then as version 1, moving on only on a `BackupUnopenedError`; a payload that opens under neither refuses with one `restore.backup-unopened` whose `authenticated` carries the version-2 values, and any other error rejects as before. The setup client's `prepareCommitSetup` seals version 2 through the constant. Changed: `BACKUP_PAYLOAD_VERSION` is now 2. New: the constants `BACKUP_LEGACY_PAYLOAD_VERSION` (1, opened, never written) and `BACKUP_READ_PAYLOAD_VERSIONS` (`[2, 1]`, the order a restore tries). The payload size, layout, padding, cipher, nonce, associated data, messages, restore codes and records, and every signature are unchanged; no closed set or frozen record changes.

Breaking: encrypted backups are now sealed as payload version 2, whose PBKDF2-HMAC-SHA256 key (600,000 iterations, unchanged) takes the 160-byte associated data of the five authenticated values as its salt instead of a zero-length salt, so one password no longer gives one key for every account and setup. `BACKUP_PAYLOAD_VERSION` is now 2. `sealBackup` throws a RangeError for any other `payloadVersion`. `openBackup` still opens version-1 payloads under `payloadVersion: 1` and refuses any version but 1 and 2 before deriving a key. `getSetup` and the recovery client's restore try version 2, then version 1, so a wrong password costs two key derivations, and `restore.backup-unopened` reports the version-2 values. Size (2501 bytes), layout, padding and cipher are unchanged. A reader of its own must add the salted derivation. New: `BACKUP_LEGACY_PAYLOAD_VERSION`, `BACKUP_READ_PAYLOAD_VERSIONS`.

Compatibility: backups already on chain stay readable, with no end date set: a restore opens a version-1 payload through its second attempt with nothing asked of the holder, and `openBackup` opens one under `payloadVersion: BACKUP_LEGACY_PAYLOAD_VERSION`. A holder's version-1 backup stays its rebuild source until it commits a setup again, whose backup is sealed as version 2. A caller of `sealBackup` that passes `BACKUP_PAYLOAD_VERSION` needs no change; one that passes the literal 1 must pass the constant. A caller of `openBackup` with its own values passes the version the payload was sealed under, or tries `BACKUP_READ_PAYLOAD_VERSIONS` in order as the restore does. A payload of the wrong length still costs no key derivation.
