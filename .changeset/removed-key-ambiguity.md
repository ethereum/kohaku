`inferRemovedKey`, and with it `recoveryState`, the setup client's `describeSetup` and `initRecoveryGathering`, no longer picks silently between two live keys. Without a supplied address the inference names its key exactly as before (the latest consumed handover's new key, else the signer of the latest setup commit, the first `isAuthority` confirms at the pinned block, with the same reads in the same order), then reads every other address it can name: the setup commit's signer where the handover named the key (with a signer recovery only), and each address whose last `LogPrivilegeChanged` write on the account, in log order from the descriptor's `deployedAt` to the pinned block with a log in a replaced block dropped, is nonzero, read with one more `fetch` over `privilegeFilter()`. It asks `isAuthority` at the pinned block of each one that differs from the key, and answers the new value `ambiguous`, appended fourth to `REMOVED_KEY_UNNAMED` (so `RemovedKeyUnnamed`, `RemovedKey`, `RecoveryState.removedKey` and `SetupDescription.removedKey` carry it), where any is confirmed; otherwise it answers the key, and a witness whose read fails or answers malformed is not confirmed and never turns the key into `unread`. `initRecoveryGathering` without a `removedAuthority` refuses an `ambiguous` key through the existing error `handover.removed-unknown`, whose values become `account`, `removedKey` and `candidates`: every confirmed address, checksummed, the named key first, then the signer, then the privilege holders in the order of their last write. The holder chooses by passing the address they lost as `Handover.removedAuthority`, which is confirmed alone with one `isAuthority`, as before, and never answers `ambiguous`. `RemovedKeyInputs.events` now picks `privilegeFilter` beside `accountFilter` and `fetch`, and `inferRemovedKey` refuses `events` without it with a `TypeError` before any read. No finding code, provider-interface method, record member or export is added.

Breaking: `REMOVED_KEY_UNNAMED`, and with it `RemovedKeyUnnamed` and `RemovedKey`, gains the value `ambiguous`, so a consumer that keeps an exhaustive map or switch over the removed key must handle it before it compiles again; the removed key now has a value for several live keys.

Breaking: `RemovedKeyInputs.events` requires `privilegeFilter`, so a caller of `inferRemovedKey` that builds its own `events` must add it; every kit `IEventManager` has it.

Compatibility: where no second address is confirmed, the answer, the init's payload and its findings are byte-identical to before, and `no-source`, `not-a-key` and `unread` keep their `handover.removed-unknown` values with no `candidates`. A named key costs more reads than before: one more log scan over the account's privilege writes, the setup commit's transaction and signer recovery where the handover named the key, and one `isAuthority` per other address named. The inference never proves the account's key set complete: a key installed by the account's creation code, or written before the deployment block, is not read, and the holder's own record of the lost key, passed as `removedAuthority`, remains the ordinary route.
