The setup client's `prepareCommitSetup` now runs setup validation inside the prepare. After its checks made before any read, it reads the read tag's block once and, at that block, makes the reads `validateSetup` makes (each method's module reads, the action's reads with `MANAGER()`, the account's fallback-handler entry where it is read, and the manager's setup notifications from the deployment block to the pinned one) beside the manager's state and the authorization read, with one `eth_getCode` for the account shared by the judgment and the authorization read. While the findings hold an error it throws a `KitRefusalError` with the constant `SETUP_CLIENT_VALIDATION_REFUSED_MESSAGE`, which 0.0.1-alpha.0 removed and which returns with its earlier text (`'the setup draft does not validate: its findings name every error'`), whose `findings` is the whole `ValidationResult` `validateSetup` returns at that block, warnings included, and which carries no `restoreCause`; it throws before the setup nonce is checked and before any backup is sealed or any call is built or simulated. Warnings never block: a draft with no error prepares as before. The prepare judges and commits one plain copy of the draft's members taken at the call (a draft held behind proxies, as reactive UI state keeps it, prepares as the plain draft does), so a change the caller makes to the draft while the prepare runs reaches neither the judgment nor the commitment. A rejected read rejects the prepare with its own error, as it rejects `validateSetup`, and so does a `TypeError` the judgment raises, such as for a registered method codec without `decodeConfig`. The refusals made before any read are unchanged and still make no provider call: `versionEscaped`, a malformed draft, password or options, a body past its ABI widths (`RangeError`) and an encrypted backup too wide to seal (`backup.too-wide`). New: the constant `SETUP_CLIENT_VALIDATION_REFUSED_MESSAGE`. `prepareClearSetup`, `confirmSetup` and the recovery client's prepares are unchanged; no type, closed set, record or signature changes.

Breaking: `prepareCommitSetup` throws on every draft for which `validateSetup` reports an error, drafts it used to seal, build and simulate, among them an empty rule, a threshold above its clause's credential count, a wait above the maximum or past its field width, a config the chain can never verify, an action that does not support the account or answers another manager, and an account with no code while `validateSetup` reports `account.not-deployed` for it.

Compatibility: an integrator that already calls `validateSetup` first and stops on an error sees the same results, at the cost of the validation reads on every prepare, the log scan among them; `validateSetup` stays the only way to read the warnings of a draft that prepares, since a prepare that succeeds returns no findings. One that committed drafts with errors must fix the draft; a setup committed with such contents could never be repaired once the key is lost. A caller who deliberately commits an unvalidated draft composes the exported parts (`setupCommitment`, `encodeSetupBody`, `sealBackup` and `PolicyManager.prepareCommitSetup`) as before.
