`validateSetup`, pure and on the setup client, now judges an account with no code whose client configuration names `accountImplementation`, the implementation it is about to be deployed with, against the implementation the action serves: the action's `AMBIRE_IMPLEMENTATION()` where it answers, else the descriptor's `servedImplementation`. A match gives no implementation-fit error (other errors, such as `action.manager-mismatch`, still apply) and the new warning `account.deploy-pending` (subject `account`, values `account`, `accountImplementation`, `servedImplementation`, and `actionImplementation` where the action answered, all checksummed), placed before `action.unaudited`; a mismatch gives the error `action.unsupported` (subject `action`, values `action`, `account`, `supportsAccount`, `accountImplementation`, `servedImplementation`, and `actionImplementation` where the action answered) and no `account.not-deployed`. An account with no code and no `accountImplementation` keeps `account.not-deployed` with unchanged values, and an account with code is judged as before. The setup client's `validateSetup` and `describeSetup` make one more `eth_call` on that declared code-less path alone, `AMBIRE_IMPLEMENTATION()` to the action from the zero address at the pinned block, after the action's other reads; a revert or an answer that does not decode as one address reads as `{ answered: false }`, any other provider rejection propagates, and the account gets no read beyond its one `eth_getCode`. `describeSetup` output is unchanged. `prepareCommitSetup` reads the account's code once, shared with its authorization read, and over an account with no code returns the atomic arming and commit batch with no `simulation` on its calls, whatever `options.simulate` or the configuration default say, since separate `eth_call`s cannot model the deployment: it is the inner batch the integrator wraps in its own deployment of the account and simulates as the transaction it composes. New: the warning code `account.deploy-pending` in `SETUP_WARNING_CODES`, after `account.fallback-handler`, the constant `RECOVERY_ACTION_IMPLEMENTATION_ABI`, and the optional member `ActionReads.actionImplementation`, a `ReadResult<Address>` that both pure functions refuse with a `TypeError` where it is present and malformed.

Compatibility: no call site needs a change. A draft over a code-less account whose configuration names the implementation the action serves, which used to get the error `account.not-deployed`, now gets in its place the warning `account.deploy-pending` and no implementation-fit error, so the account can be deployed and armed in the transaction that carries the commit; one naming another implementation now gets `action.unsupported` in place of `account.not-deployed`. A consumer that read `simulation` on a code-less commit batch, where it carried a vacuous arming success and a commit revert, now finds it absent. `ActionReads.actionImplementation` is optional, so a caller of the pure `validateSetup` or `describeSetup` with its own reads needs no change, and without it a declared code-less account is judged against the descriptor's `servedImplementation`. The closed set `SETUP_WARNING_CODES`, and with it the `WarningCode` union, grew by one member, so a consumer that keeps an exhaustive map or switch over every warning code must add `account.deploy-pending` before it compiles again; a consumer that reads findings as data is unaffected.
