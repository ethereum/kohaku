The recovery client's `prepareStartAttempt` now refuses, before any read, a handover that nobody could execute or use, judged from the payload and the client's own account, action and descriptor alone. A payload that does not decode, names the zero address as either key or names one address as both keys throws a `KitRefusalError` with `RECOVERY_CLIENT_PAYLOAD_MALFORMED_MESSAGE` and one `handover.malformed` finding (values `zeroNew`, `zeroRemoved`, `layoutDecodes` and `sameAuthority`), the refusal `prepareExecuteHandover` already makes; a payload whose new key is the account, the policy manager, the action, its kit slot or the fallback-handler entry throws a `KitRefusalError` with `RECOVERY_CLIENT_HANDOVER_REFUSED_MESSAGE` and one `handover.new-reserved` finding (values `newAuthority`, checksummed, and `reserved`), the finding `initRecoveryGathering` raises for it. Both throw before the block is pinned and make no provider or manager call; the prepare still runs no request validation and raises no warning. `prepareExecuteHandover` (a reserved new key still prepares there, since the action executes it), `prepareCancelByProofs`, the action codec, `validateRequest`, `initRecoveryGathering` and every message constant are unchanged; no type, closed set or signature changes.

Compatibility: an opening request whose payload names a zero, repeated or reserved key, which used to prepare and simulate, now throws; the attempt it opened would have held the account's single waiting slot and could never execute, or would have installed a key nobody can sign for. An undecodable payload's `handover.malformed` finding now carries `sameAuthority: false` as well, so a consumer that deep-compares its values with `{ zeroNew, zeroRemoved, layoutDecodes }` sees one more member.
