The default Aadhaar stack checks the bucket's code files and reports a failed download as `device-unavailable`. Where the artifacts' `wasmURL` and `vkeyURL` are the SDK's own bucket files, as in `METHOD_AADHAAR_BUCKET_CHUNKED` (the default) and `METHOD_AADHAAR_BUCKET_SERVER`, the installed stack fetches both once per page, before the peer's `init`, compares their sha256 with the new `METHOD_AADHAAR_BUCKET_SHA256` (`wasm`, `zkey` and `vkey` as `0x` lower hex) and hands them to the peer as object URLs. The page keeps one checked pair for each bucket wasm and vkey URL and pinned hashes: concurrent first loads share one fetch, and every later stack over the same files reuses the pair without fetching. That pair is never revoked, since the peer's page-global `init` may still read it, so the retention is bounded at one pair per files and hashes per page; a fetch, check or object URL that fails keeps nothing and revokes any object URL that load made. The zkey URL is unchanged and the zkey is not checked; its hash is for a caller holding a whole copy of its own. A failed fetch or a mismatch rejects the load with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_ARTIFACT_HASH_MESSAGE`. That reads `device-unavailable`, and the load is retried on the next call. Integrator URLs are neither fetched nor changed. The peer's `init` is page-global, so two stacks with different files on one page now take turns on the peer: before each `generateArgs`, `prove` or `verify`, a stack whose files the peer does not hold waits until every peer call in flight under the files it holds has settled, an aborted proof's included, then calls `init` again with its own files, already checked or as given, with no new fetch or check. Calls over the files the peer holds run at once and side by side, as before, while no stack with other files waits its turn; once one waits, every later call queues behind it in arrival order, so a stack with other files is not held off by a steady stream of proofs. Default stacks, which share one pair, never re-initialise each other. A proof whose signal aborts while it waits never reaches the peer, and a failed `init` reads `device-unavailable` and is tried again on the next call. That includes the `init` that `replyFrom` needs before its local verdict when a stack with other files took its turn during the proof, which now answers `device-unavailable` instead of returning the proof unverified, while any other throw from the peer's `verify` still reads `not-judged`, as an unavailable stack still does under the method's `verify`. The JSDoc of `coreStack`, `AnonAadhaarArtifacts` and `AnonAadhaarMethodOptions.artifacts` says so. The stack also records each progress state the peer reports before passing it to the page unchanged. A proof that rejects while the last state is a download state (the new `METHOD_AADHAAR_DOWNLOAD_STATES`, `fetching-wasm` and `fetching-zkey`) rejects with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_STACK_DOWNLOAD_MESSAGE`, which reads `device-unavailable`. A rejection with no state, or at or after `proving`, reads `material-rejected` as before. Under `chunked` the peer drops a zkey piece's download error, so a failed or corrupt piece still reads `material-rejected` and stays in the browser's storage under its file name until the site's data is cleared. The chunked source that last wrote a name is the one every chunked proof on the page reads. The JSDoc of `METHOD_AADHAAR_BUCKET_CHUNKED` and `AnonAadhaarMethodOptions.artifacts` says so. No closed set or record changes.

Compatibility: a download that fails under the installed stack's `server` mode, or the wasm download under `chunked`, now reads `device-unavailable` instead of `material-rejected`. Over the bucket files, the default stack now fetches the 10 MB wasm and the vkey itself, once per page, and the peer reads them from memory instead of from the bucket on every proof; that pair stays in memory for the life of the page. That uses `fetch`, `Blob` and `URL.createObjectURL`, present in browsers and in Node 22 and later. A bucket file that changes or fails to download stops proving with `device-unavailable` until it matches again. A call through a stack whose files the peer does not hold now waits for the peer's calls in flight to end instead of running at once over another stack's files. What a consumer installs, the bucket records' values and the lazy import of `@anon-aadhaar/core` are unchanged.
