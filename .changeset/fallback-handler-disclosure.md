The setup client's `validateSetup` and `describeSetup` now read the account's fallback handler. Where the account holds code, the action answers `supportsAccount` with true and the client is bound to the descriptor's own action, each judgment makes one more `eth_call` after the action's reads: `privileges(0x0000000000000000000000000000000000006969)` to the account, from the zero address at the pinned block. The pinned Ambire implementation delegatecalls the address in that word's low 20 bytes on any selector it does not know, and a recovery leaves the entry in place. `describeSetup` returns it as the optional member `SetupDescription.fallbackHandler`, a `ReadResult<DescribedFallbackHandler>`, where the new record `DescribedFallbackHandler` holds `entry`, the full word in lower case, all zero meaning no handler is installed, and `handler`, the low 20 bytes checksummed, absent where they are zero. A revert, an answer that is not one 32-byte word or a failed transport reads as `{ answered: false }` and never throws; the member is absent where nothing was read, so an account without code keeps `account.not-deployed` alone. `validateSetup`, pure and on the setup client, gives the new warning `account.fallback-handler` (subject `account`, values `account`, `slot`, `entry`, and `handler` where the low 20 bytes are not zero) on an answered nonzero word, and nothing on a zero, unanswered or absent one; it never refuses. New: the constants `RECOVERY_ACTION_PRIVILEGES_ABI` and `RECOVERY_ACTION_WORD_RETURN_ABI` (the read's key is `RECOVERY_ACTION_FALLBACK_HANDLER_SLOT`, which the handover change introduced), the warning code `account.fallback-handler` in `SETUP_WARNING_CODES`, after `manager.already-armed`, the record `DescribedFallbackHandler`, the member `SetupDescription.fallbackHandler`, and the optional member `ActionReads.fallbackHandlerEntry`, a `ReadResult<Hex>` that both pure functions refuse with a `TypeError` where it is present and malformed.

Compatibility: `ActionReads.fallbackHandlerEntry` and `SetupDescription.fallbackHandler` are optional, so a caller of the pure `validateSetup` or `describeSetup` with its own reads needs no change and gets neither the member nor the warning until it supplies the entry. The closed set `SETUP_WARNING_CODES`, and with it the `WarningCode` union, grew by one member, so a consumer that keeps an exhaustive map or switch over every warning code must add `account.fallback-handler` before it compiles again; a consumer that reads findings as data is unaffected.
