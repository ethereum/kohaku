`IEventManager.fetch`, and with it `EventManager.fetch`, now resolves to the new record `FetchedNotifications`, `{ notifications, skipped }`, and no longer rejects the whole read for one log it cannot decode. A log from an address the reader owns (the manager, the bound account whatever code emitted it, a method the descriptor names or the registry is keyed on) whose first topic names a kit event but whose layout the event's decoder refuses, such as a wrong topic count, data that does not decode or an impossible cancel combination, is listed in `skipped` as the new record `SkippedLog`, `{ at, log, error }`: `at` is its position as a notification would carry it, `log` the log as the provider returned it and `error` the value the decoder threw, unchanged. Every chunk of the range is still read, `notifications` holds every log that decoded, and both lists come back sorted by log position. A chunk the provider rejects, an answer that is not a list of logs, a log whose fields are not strings and a range out of order still reject the read; an unowned log, or an owned log whose first topic names no kit event, still yields nothing and is not listed. `decodeLog` is unchanged and still throws on such a log. The SDK's own reads of the manager's events refuse a read that skipped a log, as they did before: `restoreConfiguration` by password (and with it `getSetup`, `initRecoveryGathering` and `initCancelGathering`), `confirmSetup`, and the setup client's `validateSetup` and `prepareCommitSetup` reject with the first skipped log's `error`, and `inferRemovedKey` (and with it the removed key that `describeSetup`, `recoveryState` and the handover of `initRecoveryGathering` read) answers `'unread'`. New: the records `FetchedNotifications` and `SkippedLog`.

Breaking: `IEventManager.fetch` resolves to `FetchedNotifications` instead of `readonly KitNotification[]`, so a caller of `fetch` reads `.notifications`, and an `IEventManager` handed to `withEventManager` or to `inferRemovedKey` must resolve the record; one that still resolves a bare array makes the SDK's own reads throw a `TypeError` (`'unread'` from `inferRemovedKey`), never read as a quiet account.

Compatibility: a range without such a log reads exactly as before, in `.notifications`. A watcher that kept refetching a range that never read can now move its cursor past it and record or alert on each `skipped` entry, which every read reports once with its position. `NOTIFICATION_KINDS`, `KitNotification`, the three filters, `decodeLog` and the builder's member check are unchanged.
